# AI 出题后为什么要"人工审核"：人机协同工作流设计

> 系列：面试题训练系统开发实录 · v1.2
> 关键词：状态机 / 人机协同 / 生成式 AI 质量控制 / 一致性口径

---

## 1. 背景：AI 生成的题目能直接用吗

系统接入了 LLM 出题后，一个现实问题浮出水面：**模型输出存在不确定性**。同一段知识库内容，两次生成可能得到措辞不同、甚至事实有偏差的题目；规则引擎降级模式下的题目质量更是参差不齐。如果生成即入库、入库即可组卷，用户做到烂题时没有任何补救手段。

v1.2 因此引入**出题审核流**：AI 生成的题先进入待审核队列，人工确认（或修正后确认）才进入组卷池。这篇文章记录其中的设计决策。

## 2. 核心设计：三态状态机

题目增加一个维度：`review_status`。

```text
pending ──approve──▶ approved ──?──▶ （组卷池）
   │                     ▲
   │                     │ 编辑后通过
   ├──reject──▶ rejected│
   │                     │
   └─────── 重新审核 ◀──┘（预留）
```

状态流转的操作集合：

| 操作 | 语义 |
|---|---|
| `approve` | 单题通过，进入组卷池 |
| `reject` | 单题拒绝，不进池 |
| 编辑后通过 | 修正题干/选项/答案/解析 → 保存 → 自动通过 |
| 批量 approve/reject | 按 id 列表批量流转（如"整份资料一键通过"） |

### 2.1 为什么拒绝态要保留而不是删除

拒绝的题目仍有价值：它记录了"AI 在哪些内容上容易出错"，是后续优化 prompt 的语料。软状态（rejected）优于物理删除，也是审计友好的做法。

### 2.2 被引用的题目禁止删除

考卷引用题目后，删除题目会让历史成绩失去题目快照。规则：**只要题目出现在任意考卷中，禁止物理删除**，只能改状态。这与"拒绝态保留"共同保证历史数据完整。

## 3. 编辑校验：状态流转的质量闸门

"编辑后通过"是审核流里最能体现工程价值的功能——它把人的修正变成一次**带校验的写入**。选择题尤其容易出错（改了选项忘了改答案），校验规则：

- 选择题：恰好 4 个非空选项；答案字母 ∈ {A,B,C,D}；保存时统一补全 `A. ` 前缀，保证前端渲染与答案字母一致
- 填空题：题干必须包含 `______` 空位（可用正则检测）；答案非空
- 判断题：答案 ∈ {正确, 错误}
- 难度：∈ {easy, medium, hard}

**先校验、后落库、再流转状态**——顺序不能反。若先流转再校验失败，会留下"approved 但内容非法"的脏数据。

## 4. 一致性口径：比状态机更容易翻车的地方

引入审核态后，系统里所有"题目数量"相关的口径都要重新审视。这是本次迭代修Bug最密集的区域：

| 场景 | 口径 |
|---|---|
| 组卷抽题 | 只抽 `approved` |
| 知识条目卡片上的"题目数" | 只统计 `approved`（与组卷池一致） |
| 题目分析看板的总量/分布 | 只统计 `approved`，另单独展示 `pending_count` |
| 题库列表 | 按 Tab 分态展示（默认已通过） |

**教训：新增一个状态维度时，第一件事不是写 CRUD，而是全局搜索所有 `count(questions)` 的地方，逐个确认口径。** 漏一处的典型症状是：页面上显示 45 题，组卷时却提示"仅 1 道可用"。

## 5. 前端设计：让待审数量"可见"

审核流要真正运转起来，用户必须随时知道"有多少题在等审核"：

- 侧边栏「题目审核」菜单挂 **Badge 徽标**（待审数），30s 轮询刷新
- 审核页顶部大数字 + 表格多选，支持批量操作，降低"一篇篇点通过"的疲劳
- 题库页分 Tab，待审/已拒题目有明确的去处，不是黑盒

轮询 vs WebSocket：单用户演示系统 30s 轮询足够；多用户协作场景才值得上推送。**按量级选方案，不超前设计。**

## 6. 经验清单

1. AI 生成内容入生产环境前，留一个人工确认的闸门——这是成本最低的质量控制
2. 软状态（rejected）优于物理删除，保留失败样本就是保留优化语料
3. 历史引用的数据禁止删除，用状态机表达生命周期
4. 校验必须先于状态流转，否则产生脏数据
5. 新增状态维度的第一课：全局排查计数口径
6. 人机协同产品的 UI 重点是"让待办可见"——徽标、批量、分组

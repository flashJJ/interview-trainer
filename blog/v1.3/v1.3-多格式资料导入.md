# 让 AI 读你的 PDF 和网页：多格式资料导入的提取与避坑

> 系列：面试题训练系统开发实录 · v1.3
> 关键词：文档解析 / 正文提取 / readability / 错误路径设计

---

## 1. 背景：知识库录入不该被格式卡住

训练系统的第一步是"资料入库"。v1.0 只支持粘贴文本和 .txt/.md 文件——但真实世界的技术资料是 PDF 电子书、Word 笔记和网页文章。v1.3 把录入扩展到三种新来源，本文聚焦其中的提取技术与错误路径设计。

## 2. 三种格式，三种提取策略

### 2.1 PDF：pypdf 提取文本层

```python
reader = PdfReader(io.BytesIO(raw))
for page in reader.pages[:200]:      # 页数上限防护
    text = page.extract_text() or ""
```

要点与坑：

- **PDF 是版式文档不是文本文档**：能提取的前提是"有文本层"（文字型 PDF）。扫描件/图片型 PDF 提取结果为空——这不是 bug，是物理限制。**明确告知用户"暂不支持 OCR"，而不是返回空内容让用户困惑**
- **加密 PDF**：先尝试空密码解密（很多"加密"只是设置了权限口令），失败则明确报错
- **单页失败不阻塞整体**：个别页损坏时跳过该页，而不是让整个文件失败
- **页数上限**：`pages[:200]` 防止几百页的大书把内存打爆

### 2.2 DOCX：python-docx 提取段落与表格

DOCX 结构规整（OOXML），提取比 PDF 简单得多，但有个常见遗漏：**表格**。技术笔记里大量内容以表格存在（状态码表、参数对照表），只提取 `document.paragraphs` 会丢掉半个文档：

```python
for table in document.tables:
    for row in table.rows:
        cells = [c.text.strip() for c in row.cells if c.text.strip()]
        parts.append(" | ".join(cells))    # 行内单元格用 | 连接，保留二维结构
```

### 2.3 网页：readability-lxml 提取正文

网页是最脏的来源——导航栏、广告、评论区、页脚版权声明混在一起。核心武器是 **Readability 算法**（ Firefox 阅读模式的同款思路）：

1. 解析 DOM，对每个候选节点（`<p>`、`<div>`）按内容特征打分：段落数量、文本长度、逗号/句号密度（正文有标点，导航没有）
2. 综合自身分与父/子节点分，取得分最高的容器
3. 提取容器 HTML，去标签转纯文本

实测效果：一篇带导航+广告+页脚的技术文章，提取后正文完整、噪声行基本清零。残留的个别噪声（"登录/注册/版权所有"）用一行正则兜底过滤。

```python
text = re.sub(r"<script[\s\S]*?</script>|<style[\s\S]*?</style>", " ", html, flags=re.I)
# ...去标签、解码实体、按行过滤噪声正则
```

## 3. 网络抓取：直连还是走代理

URL 抓取的一个隐蔽陷阱：**HTTP 客户端默认读取系统代理环境变量**。在办公网/VPN 环境下，抓取一个公网 URL 时代理会正常转发；但抓取内网 wiki 或本地服务时，代理会直接拒绝连接。

本项目的决策：**抓取客户端 `trust_env=False`（直连目标地址）**。理由：

- 录入的链接绝大多数是公网文章，直连即可达
- 内网/本地地址（自建文档站）是知识库的重要来源，不能被代理误伤
- 代理该不该用，交给用户机器的网络层决定，不由代码假设

配套的防护：超时 30s、重定向上限 5 次、响应体 10MB 上限、带浏览器 UA（部分站点对非浏览器 UA 返回 403）。

## 4. 错误路径设计：比 happy path 更重要

多格式导入的失败模式极多，每一种都要给出**人类可读的原因**，而不是把堆栈甩给用户：

| 失败场景 | 用户看到的信息 |
|---|---|
| 非 PDF/DOCX 文件 | "仅支持 .txt / .md / .pdf / .docx 文件" |
| 文件损坏 | "PDF 解析失败（文件可能损坏或非 PDF 格式）" |
| 扫描件 PDF | "未能从 PDF 提取到文本（可能是扫描件/图片型 PDF，暂不支持 OCR）" |
| 空 DOCX | "DOCX 内容为空或过少" |
| 非法协议 URL | "URL 必须以 http:// 或 https:// 开头" |
| 页面 404/403 | "网页返回错误状态 404" |
| 连接超时 | "抓取超时（30s）" |
| 需登录/动态渲染 | "网页正文提取结果过少（可能需要登录或为动态渲染页面）" |
| 内容过少 | "文件内容太少（至少 30 字符）" |

设计原则：**错误信息要包含"原因 + 可能解法"**。"可能是扫描件（不支持 OCR）"比"提取失败"有用一个量级。

## 5. 与既有链路的关系：解析只是新 source

多格式导入没有碰处理流水线——分块、关键词、向量化对任何来源一视同仁。新格式只是给流水线喂了新的文本：

```text
文本粘贴 / .txt / .md ┐
.pdf ──pypdf───────────┤
.docx ─python-docx─────┼──▶ 统一 process_entry：分块→关键词→向量化→可出题
.url ──httpx+readability┘
```

`source_type` 从 `text|file` 扩展为 `text|file|url`，仅此而已。**扩展点时优先想"如何让新来源汇入既有管道"，而不是为每种来源造一条管道。**

## 6. 测试：单测 + 真实链路双管齐下

- **单测**：用 python-docx 现场生成 DOCX 做往返验证；HTML 用样例字符串（含 script/style/导航/页脚）验证提取与去噪；PDF 用损坏字节验证报错
- **真实链路**：本地起 HTTP 服务提供测试网页，走完整"URL 录入→处理→出题"；DOCX 上传后核对正文关键内容与表格是否入库
- **错误路径**：非法协议、连接拒绝、错误扩展名各一条断言

样例字符串测 HTML 是性价比极高的手段——它把"网页千变万化"收敛为"几种 DOM 模式"，无需联网即可覆盖主路径。

## 7. 经验清单

1. PDF 只处理文本层，扫描件明确拒绝并说明原因
2. DOCX 别忘了表格，那是技术资料的重灾区
3. 网页正文用成熟算法（readability），别手写规则
4. 抓取默认直连，代理交给网络层
5. 错误信息带原因和出路，是产品体验的一部分
6. 新来源汇入既有管道，扩展 source_type 而非复制流水线
7. 测试用内存构造替代真实文件（docx 现场生成、HTML 样例串）

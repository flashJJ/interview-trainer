# 容器化一个 SQLite 项目：四个只在 Docker 里才暴露的坑

> 版本：v1.9 ｜ 主题：工程化 / 容器化 ｜ 关键词：Docker Compose、SQLite 路径、named volume、隐式依赖、nginx 反代

## 1. 背景：本地跑得好好的，为什么一进容器就出事

这个项目是 FastAPI + SQLite + ChromaDB + React 的单体应用，本地用 `uvicorn` + `vite dev` 跑了八个版本，一次都没出过事。

真正动手写 Dockerfile 时，才发现「本地能跑」和「换台机器能跑」是两件完全不同的事。下面四个坑，全部是**本地永远复现不了、容器里必现**的类型。

---

## 2. 坑一：`sqlite:///` 少一个斜杠，数据就没了

SQLAlchemy 的 SQLite 连接串对斜杠数量极其敏感：

| 写法 | 实际含义 |
|---|---|
| `sqlite:///./data/app.db` | **相对路径**，相对「进程当前工作目录」 |
| `sqlite:////app/data/app.db` | **绝对路径** `/app/data/app.db`（4 个斜杠） |

容器里如果写成三个斜杠 + 相对路径，数据库会落到镜像的可写层（`/app/data/app.db` 也在层里，但**不在挂载的卷里**）。表现是：

- 容器重启 → 数据「消失」（其实还在旧容器层，`docker compose down` 后彻底没）；
- 你 `docker compose exec` 进容器看卷目录，发现是空的，以为卷没挂上。

**结论**：容器里一律用绝对路径 + 四个斜杠，并且在 compose 里显式写死，不依赖工作目录。

---

## 3. 坑二：Windows bind mount 上的 SQLite，WAL 会咬人

SQLite 默认在项目里开 WAL 提升并发读。WAL 依赖三个文件：`.db`、`.db-wal`、`.db-shm`，而且需要**同目录下的文件锁**。

把宿主目录 bind mount 进容器（`./data:/app/data`）在 Linux 下通常没问题，但在 Docker Desktop（Windows/macOS）上，文件系统是跨 VM 的转发层，`fcntl` 锁语义与原生 ext4 不同，常见症状：

- `database is locked` 偶发，且只在并发请求时出现；
- WAL 文件持续增长不 checkpoint；
- 删了 `.db-wal` 后数据对不上。

**做法**：用 **named volume**（`app-data:/app/data`），让数据落在 Docker 自己的卷里；备份用 `docker run --rm -v app-data:/data alpine tar czf - -C /data .` 导出，不要直接挂宿主目录。

代价是「想在宿主机直接打开 db 文件」不方便——这恰好也是好事，避免误改线上数据。

## 4. 坑三：本机能过、容器必挂的隐式依赖

最隐蔽的一个。`npm run build` 本地通过，镜像构建时却报：

```
vite.config.ts(3,36): error TS2307: Cannot find module 'node:url'
```

`package.json` 里明明没有 `@types/node`，本地为什么不报错？

因为 **Node 的模块解析会向上遍历父目录**：本地仓库恰好放在一个装有 `node_modules` 的目录下（三层之上一份 `@types/node`），`tsc` 顺着往上找到了它。容器里只有 `COPY` 进来的 `frontend/` 目录，没有「上层」，于是立刻失败。

这类问题的通用形态是：**依赖没有声明，但本地环境恰好提供了**。同类的还有：

- 全局安装的 CLI（`tsc`、`prettier`）被 `npx` 悄悄用上；
- Python 里 `pip install` 顺序导致的传递依赖，卸载主包后仍在；
- 系统库（`libgomp1`、`libstdc++`）本机有、slim 镜像没有。

**做法**：
1. 缺什么就显式装什么（`npm i -D @types/node`），别依赖上层目录；
2. **把镜像构建放进 CI**——这是唯一能稳定复现「干净环境」的方式；
3. 构建阶段装上编译工具链（builder 阶段），运行阶段只留运行时库（如 `libgomp1`），别把 gcc 带进最终镜像。

## 5. 坑四：nginx 静态 `proxy_pass` 只在启动时解析一次

反向代理想当然写成：

```nginx
location /api/ { proxy_pass http://backend:8000; }
```

`backend` 是 compose 的服务名，由 Docker 内置 DNS 解析。问题在于：**nginx 只在启动时解析一次并缓存 IP**。后端容器重建（`docker compose up -d --force-recreate`、崩溃重启换 IP）后，nginx 仍然往旧 IP 发请求，表现是整站 502，而 `docker compose ps` 显示两个容器都健康。

解法是让 nginx 每次请求都重新解析：

```nginx
resolver 127.0.0.11 valid=10s ipv6=off;   # Docker 内置 DNS
set $api_upstream http://backend:8000;
proxy_pass $api_upstream;                  # 变量形式才会触发重解析
```

顺带两个必须配的：

- **SSE 必须关缓冲**：AI 讲题是 `text/event-stream` 流式输出，`proxy_buffering on`（默认）会让前端等到整段结束才收到第一个字；
- **上传上限**：`client_max_body_size 20m`，要和后端解析 PDF/DOCX 的上限对齐，否则用户看到的是 nginx 的 413 而不是业务报错。

## 6. 收尾：把「能跑」变成可验收的标准

容器化最容易自欺欺人的地方是「我 `up` 起来了，页面能打开」。所以验收得写死几条可判定的：

| 验收项 | 判定方式 |
|---|---|
| 健康就绪 | 冷启动后 `/api/health` 返回 200，且 compose 的 `depends_on: service_healthy` 生效 |
| 数据不丢 | `docker compose restart` 后原账号还能登录；`down`（不带 `-v`）不丢卷 |
| 非 root | `docker compose exec backend id -u` 输出不是 0 |
| 配置兜底 | 不设 `JWT_SECRET` / 仍为占位值时，容器**明确报错退出**而不是带病启动 |
| 冒烟可复用 | 同一份冒烟脚本，靠 `SMOKE_BASE` 切换「本机 8000」和「容器 8080」 |

最后一条尤其值得做：**别为容器另写一套测试**。让既有脚本通过一个环境变量指向不同地址，比维护两份断言可靠得多。

---

## 7. 小结

| 坑 | 一句话对策 |
|---|---|
| SQLite 相对路径 | 容器里一律 `sqlite:////` 绝对路径 |
| bind mount + WAL | 用 named volume，备份走 tar 而不是挂宿主目录 |
| 隐式依赖 | 缺的显式声明；把镜像构建放进 CI 当「干净环境」探针 |
| nginx DNS 缓存 | 变量 `proxy_pass` + `resolver`；SSE 关 `proxy_buffering` |

四个坑的共同点：**本地环境的「额外馈赠」（上层 node_modules、系统库、相对路径的巧合）在容器里全部消失**。容器化真正的价值不是「多了一种启动方式」，而是把这些巧合一次性挤干净。

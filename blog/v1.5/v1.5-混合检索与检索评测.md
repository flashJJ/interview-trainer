# 混合检索与检索评测：把「感觉更准了」变成可复现的数字

> 版本：v1.5 ｜ 主题：RAG 检索增强 ｜ 关键词：BM25、RRF、查询改写、Recall@K、评测集泄漏

## 1. 背景：一个从来没被验证过的检索

做 RAG 项目时，最容易糊弄自己的地方就是检索环节。改完参数刷新页面，看一眼返回结果"嗯，挺相关的"，就算优化完成。但两个问题从来没被回答：

1. 换掉向量模型/调了阈值之后，召回率到底变好了还是变差了？
2. 混合检索里的"混合"，权重凭什么定成 1:1？

本文记录一次把检索从黑盒变成可度量模块的过程，以及过程中踩到的两个反直觉的坑。

## 2. 知识点一：你的"向量检索"可能根本没有语义能力

先说一个容易被忽略的事实：**向量检索不等于语义检索**。

零配置方案里常见的做法是用字符 n-gram 的哈希向量（把中文按 2/3-gram 切碎后哈希到固定维度）。它确实能算相似度，但本质仍是词面重合度——"高可用"和"故障转移"在它的向量空间里毫无关系。

这类向量甚至比 BM25 更弱：

- BM25 有 IDF，罕见词权重高；哈希向量对所有 term 一视同仁。
- BM25 有长度归一化，短而聚焦的文档得分更高；余弦相似度对长文档天然有利。
- 哈希会碰撞，不同 n-gram 落到同一维度相互干扰。

所以"有向量库"≠"有语义检索"。前者是存储形态，后者取决于 embedding 模型的能力。

**可落地的判断方法**：拿两条意思相同但用词完全不同的句子，算一下相似度。如果相似度低，你的向量就是词法的。

## 3. 知识点二：BM25 的三个实现细节

BM25 是 1994 年的老算法，但几个细节决定了实现是否可用：

```
idf(t)     = ln(1 + (N - df(t) + 0.5) / (df(t) + 0.5))          # ① Lucene 变体
score(q,d) = Σ_t idf(t) · tf(t,d)·(k1+1) / (tf + k1·(1-b+b·|d|/avgdl))   # ②③
k1 = 1.5, b = 0.75
```

**① IDF 必须恒为正。** 经典公式 `ln((N-df+0.5)/(df+0.5))` 在某个词出现在超过一半文档里时会变成负数，导致"包含该词的文档反而被扣分"。加个 `1+` 是最简单的修复。

**② 长度归一化不是可选项。** 去掉 `b` 项后，长文档会因为 term 多而占便宜，检索结果会退化成"按文档长度排序"。

**③ 中文不需要分词器也能用。** 字符 2/3-gram 直接作为 term，配合 IDF 就能让真实术语在排名中胜出——因为术语的 n-gram 组合天然比其他词的组合更罕见。这省掉了分词词典的依赖，也避免了一堆 OOV 问题。

工程上还有一点：**别每次查询都重算整个语料的统计量**。索引要缓存，缓存要有明确的失效条件。用「语料块数 + 最大块 ID」做版本号是个便宜且够用的方案（前提是块属于"整体生成、整体删除"的生命周期）。

## 4. 知识点三：为什么融合用 RRF 而不是分数加权

两路召回要合并，第一反应是"归一化后加权求和"。问题是：

- 余弦相似度的分布集中在 0.6~0.9，BM25 是 2~10 的无界值；
- Min-Max 归一化会被单条异常值带偏，换一批语料分布就变；
- 每次调权重都要重跑一遍人工判断。

RRF（Reciprocal Rank Fusion）只看名次：

```
RRF(d) = Σ_i w_i / (k + rank_i(d))     k = 60
```

好处是彻底与分数量纲解耦，`k=60` 这个取值在大多数语料上都工作良好，唯一需要调的是通道权重 `w_i`——而这个恰好可以用评测集量化（见第 6 节）。

## 5. 知识点四：评测集设计里最致命的坑——泄漏

这是本文最想让读者带走的一点。

第一版自动评测集是这样生成的：取知识块内 TF 最高的 3 个词，拼成"XX YY ZZ 是什么"作为查询，期望命中该块。

结果：纯向量、纯 BM25、混合三种模式的 Recall@5 **全部是 1.000**。

看似完美，实际毫无意义——**查询里包含了答案块的原词**，任何词法匹配都能 100% 命中。这种评测集只能证明"检索器不是坏的"，不能证明"哪个更好"。

修复办法是让查询**改述**而不是抄词：让 LLM 读一段资料后，换一种说法提出一个技术问题（"Redis 串行处理请求为何高效，数据落盘与键失效怎样实现？"），期望块仍是原文块。

改完之后指标立刻分化：纯向量 Recall@5 只有 78.6%，BM25 100%。区分度回来了，评测才真正开始工作。

**通用原则**：评测集的查询必须与语料**在表达层面不同、在语义层面相同**。任何从语料直接抽取构造的查询，都天然对词法检索有利。

另一个配套原则是**承认残留偏差**：即使 LLM 改述，查询仍源自语料本身（同源），指标绝对值偏乐观。所以结论口径应该是"同一批次内的横向对比"，而不是"我们的召回率是 93%"。

## 6. 实测：通道越多不等于越好

固定 19 个知识块、14 条 LLM 改述查询、`top_k=5`，跑四档：

| 模式 | Recall@5 | MRR@10 | Hit@1 |
|---|---|---|---|
| 纯向量 | 78.6% | 0.482 | 28.6% |
| 纯 BM25 | 100% | 0.929 | 85.7% |
| 混合（权重 1:1） | 100% | 0.762 | 57.1% |
| 混合 + 改写 | 100% | 0.881 | 78.6% |

三个结论，每一个都和直觉相反：

**① 混合把召回补齐了。** 78.6% → 100%，补回来的正是"精确术语"型查询——哈希向量把它们拉平了，BM25 靠术语命中救回来。

**② 但等权融合把排名质量拉低了。** 混合 MRR 0.762 低于纯 BM25 的 0.929。原因不复杂：RRF 只信名次，而弱通道的名次是噪声，噪声会把原本排第一的正确结果往后推。**融合不是"多一路总比少一路好"，弱通道要付代价。**

**③ 降权立刻修复，而这是评测集带来的收益。** 把向量通道权重从 1.0 降到 0.5：

| 模式 | Recall@5 | MRR@10 | Hit@1 |
|---|---|---|---|
| 混合 | 100% | 0.917 | 85.7% |

MRR 从 0.762 提到 0.917，Hit@1 从 57.1% 提到 85.7%，召回不掉。这个 0.5 不是拍脑袋来的，是在评测集上扫出来的（1.0 / 0.8 / 0.6 / 0.5 / 0.4 / 0.3 / 0.0 逐档跑）。

顺带一个发现：**查询改写的收益取决于另一条通道有多弱。** 等权时改写把 Hit@1 从 57.1% 拉到 78.6%；权重降到 0.5 后，改写与不改写完全持平——因为此时 BM25 已经足够强，改写带来的额外检索式没有增量信息。同一个技术手段，在不同配置下价值完全不同，这也只有做过对比才知道。

## 7. 知识点五：三个指标各自在说什么

只用 Recall 会误判，只用 MRR 会忽略召回漏失。三者要一起看：

| 指标 | 定义 | 反映什么 | 什么时候会失真 |
|---|---|---|---|
| Recall@K | 命中期望块 / 期望块总数 | 有没有漏 | 期望块标错或过于宽松时虚高 |
| MRR@10 | 首个命中名次倒数均值 | 好结果排得够不够前 | 只关心第一个，忽略其余 |
| Hit@1 | 首位即命中的比例 | 用户第一眼看到的对不对 | 同上，且对 single-hit 场景过严 |

一个典型组合：Recall 100% 但 Hit@1 57%，说明"东西都在，就是没排在最前面"——这是排序问题，不是召回问题。分清了才知道该改融合权重，而不是去换 embedding。

## 8. 工程细节：两个让功能可用的实现

**① LLM 生成评测集必须并发。** 单条改述实测 16~40 秒，14 条串行要 8 分钟，用户体验等同卡死。线程池 6 并发后降到 2.5 分钟。注意写入仍放在主线程串行——SQLite 并发写会锁。

**② 评测时复用 embedding。** 同一条查询要在 3~4 个模式下重复检索，如果不缓存，embedding 调用次数是 `用例数 × 模式数 × 查询式数`。加一层按查询文本的缓存后降到 `用例数 × 查询式数`。

## 9. 经验清单

1. **先有度量，再谈优化。** 没有评测集的"检索优化"全是心理安慰。
2. **评测集的查询必须改述。** 从语料里抽取构造的查询必然泄漏，指标会集体 100%。
3. **承认指标偏差并在结论里写明口径**，比追求好看的绝对数字更专业。
4. **混合检索的权重需要实测**，1:1 不是默认正确值；弱通道会以 RRF 名次噪声的形式拖累排序。
5. **召回和排序要分开诊断。** Recall 高而 Hit@1 低是排序问题，两者都低才是召回问题。
6. **字符 n-gram + BM25 是中文零依赖检索的可靠基线**，在接入真正语义模型前，它经常打得过"假语义"向量。
7. **把评测集固化下来**（存库而不是临时脚本），换 embedding 后端时重跑一遍即可验证收益——这是让后续优化可复现的前提。

## 10. 遗留问题

- 评测集自动生成仍有同源偏差，手工用例缺少批量导入。
- 最优权重依赖 embedding 后端，因此没有固化为系统配置，而是启动评测时按需传入。
- 检索尚未接入生成链路（出题侧仍直接使用指定资料的全部块），这是下一版的重点。

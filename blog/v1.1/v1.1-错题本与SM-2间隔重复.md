# 从零实现错题本：SM-2 间隔重复算法的工程落地

> 系列：面试题训练系统开发实录 · v1.1

## 1. 背景：为什么需要错题本

考试系统里，"提交-评分-看解析"只完成了训练闭环的一半。认知科学研究表明：**在遗忘临界点主动回忆**，记忆保持率远高于集中刷题。间隔重复（Spaced Repetition）就是把这套理论工程化的方法——答错的题不是看完解析就结束，而是按算法排定的节奏重新出现。

本文记录在面试题训练系统中落地 SM-2 算法的完整过程：算法原理、数据模型、与既有考试链路的复用设计，以及那些文档里不会告诉你的边界细节。

## 2. SM-2 算法核心

### 2.1 模型

SM-2（SuperMemo 2，1987）为每道记忆项维护三个状态：

| 状态 | 含义 | 初始值 |
|---|---|---|
| `EF`（easiness） | 难易度系数，越高间隔增长越快 | 2.5 |
| `interval` | 当前复习间隔（天） | 1 |
| `repetitions` | 连续答对次数 | 0 |

### 2.2 递推规则

每次复习后按作答质量 `q`（0~5）更新：

```
if q >= 3:  # 答对
    interval = 1            if repetitions == 0
             = 6            if repetitions == 1
             = interval * EF otherwise
    repetitions += 1
else:       # 答错
    repetitions = 0
    interval = 1

EF = EF + 0.1 - (5 - q) * (0.08 + (5 - q) * 0.06)
EF = clamp(EF, 1.3, 2.5)
```

三个关键设计直觉：

1. **前两次间隔固定（1 天、6 天）**：初期样本不足，让算法先"观察"两次再按 EF 放大
2. **答错重置而非归零**：`repetitions` 清零但 EF 保留——你只是暂时忘了，不是这道题变难了
3. **EF 上下浮动且有钳制**：反复答错 EF 趋近 1.3（间隔最短），反复答对趋近 2.5；钳制防止 EF 衰减到间隔永不复发的极端值

### 2.3 质量分 q 的映射

考试场景的天然输入是"得分率"（0~1），需要映射到 0~5 的整数档位。实践中取：

```
q = round(rate * 5)     # 满分=5，半分≈3（答对档下限），0 分=0
```

一个容易踩的坑：**Python 的 `round()` 是银行家舍入**，`round(2.5) == 2` 而不是 3。半分题会掉到"答错档"，导致排期意外重置。正确写法是 `int(rate * 5 + 0.5)`。这类"语言特性与算法预期不符"的坑，单测里一定要覆盖边界值。

### 2.4 掌握判定

连续答对本身不等于永久掌握。工程上的判据是**双条件**：

```
repetitions >= 3 且 interval >= 21 天  =>  移出错题本
```

即：最近三次复习全对，且复习间隔已被算法拉长到 3 周——说明记忆进入长时保持阶段。这个阈值来自 Anki/SM-2 社区的常见实践，可按产品调整。

## 3. 数据模型与链路复用

### 3.1 错题表

```text
wrong_questions
├── user_id + question_id     （联合唯一索引）
├── error_count               错误次数（展示与排序）
├── easiness / interval_days / repetitions / due_date    SM-2 四状态
└── last_error_at / created_at
```

### 3.2 关键设计：复用考试链路，不建新表

复习模式天然就是"一次考试"：有卷子、有会话、有提交、有评分。为它单独建一套表会带来双份的提交/评分/统计逻辑。方案是给现有链路加一个**模式维度**：

- `exam_sessions.mode = exam | review`
- 复习卷就是一张 `exam_papers`（config 里标 `mode: review`），题目从到期错题随机抽取
- 提交后评分逻辑完全不变，只是 `update_after_submit` 时按模式分流：

```text
提交
 ├─ exam 模式：错题入本/error_count+1/SM-2 降档；答对不动排期
 └─ review 模式：答对升档（达掌握判据则移出）；答错降档
```

这个"模式复用"的思路适用于大多数"相似流程不同语义"的场景：**优先扩展维度，而非复制链路**。

### 3.3 提交后的副作用放在哪

错题更新是提交评分的副作用。两种放法：

1. 塞进评分函数里——评分函数变胖，且单测要连带 DB
2. 评分提交后单独调用 `update_after_submit(db, session, results)`——职责分离，算法可独立单测

选 2。副作用函数只依赖"结果列表"（question_id/score/max_score/is_correct），不关心分数怎么来的——这也是它能用内存 SQLite 做集成测试的原因。

## 4. 测试策略

算法层（纯函数）与集成层（DB 副作用）分开测：

- **算法层**：EF 升降档、clamp 边界、前两次间隔固定值、掌握判定
- **集成层**：内存 SQLite 建表，验证"答错入本→重复答错 error_count 累积→复习答对直至移出"的完整生命周期，以及"考试答对不扰动排期"的隔离性

特别值得写的一个用例：**考试模式答对应保持 interval 不变**——否则用户反复考试刷同一道错题，反而会不断推迟它的复习日，与算法意图相悖。

## 5. 经验清单

1. 语言级舍入模式（银行家舍入）与算法预期不符，边界值必须单测
2. 状态机初始值要想清楚：`due_date = 今天 + 1 天`（SM-2 标准是错后第 1 天复习），不要设成"当天可复习"造成认知负荷
3. "掌握"是产品决策不是算法输出——把判据做成常量，方便调
4. 副作用与主流程分离，是算法可测的前提
5. 相似流程优先扩展模式维度，拒绝链路复制

# 按比例分配整数名额：难度自适应组卷里的整数规划小技巧

> 版本：v1.8 ｜ 主题：算法工程 / 整数分配 ｜ 关键词：自适应组卷、整数名额分配、余数回补、库存回补、不静默凑数

## 1. 背景：用户要的是「比例」，不是「随机」

组卷功能最早只有「纯随机」：从题库里不重复抽 N 道题。能用，但有两个痛点：

1. **想要难度分布时只能手动算**——「给我 10 道题，易 2 / 中 6 / 难 2」，得先数清楚题库里各难度各有多少，再手填数量。
2. **纯随机抽出的卷子难度飘忽**——可能 10 道全是易，也可能全难，练不出「针对性」。

v1.8 加了一层「难度蓝图」：用户只选蓝图（入门 / 夯实 / 均衡 / 冲刺），系统按预设比例把题量拆到三档难度自动抽。

听起来就是一道小学乘除法，但真写起来有三个坑，每一个都会变成线上 bug：

- 浮点乘法算出的名额加起来**不等于总数**（丢了 1 题或多出 1 题）；
- 余数该补给谁，**补错了会改变难度倾向**；
- 某档题目不够时，**悄悄少抽几道**——用户以为做了 10 题，实际只做了 7 题。

下面把这套「整数名额分配 + 库存回补」讲清楚。

## 2. 知识点一：整数名额分配——为什么不能直接用浮点乘法

最直觉的写法：

```python
weights = {"easy": 0.20, "medium": 0.55, "hard": 0.25}
targets = {d: count * weights[d] for d in weights}  # 10 * 0.55 = 5.5
```

`targets` 是 `{easy: 2.0, medium: 5.5, hard: 2.5}`。问题在于：

- 题量必须是整数，5.5 题不存在；
- `int(5.5) = 5`，三档 floor 相加 `2 + 5 + 2 = 9`，**比原来少了 1**；
- 如果总题量更大，floor 累计误差会更多。

正确做法分两步：**先全部向下取整，再把「丢掉的余数」逐个补回去**。这样能保证 `sum(targets) == count` 严格成立。

```python
def allocate(count, blueprint):
    weights = BLUEPRINTS[blueprint]
    raw = {d: count * weights[d] for d in DIFFICULTIES}
    floor = {d: int(raw[d]) for d in DIFFICULTIES}
    remainder = count - sum(floor.values())   # 需要补回的名额
    order = sorted(DIFFICULTIES, key=lambda d: (-weights[d], d))  # 权重大的优先
    i = 0
    while remainder > 0:
        floor[order[i % len(order)]] += 1
        remainder -= 1
        i += 1
    return floor
```

`remainder` 一定在 `[0, len-1]` 之间（len=3，所以最多补 2 个），循环必定终止。验证几个边界：

| count | blueprint | floor（取整后） | remainder | 结果 |
|---|---|---|---|---|
| 10 | intro | 易6 中3 难1 | 0 | 易6/中3/难1 |
| 20 | consolidate | 易4 中11 难5 | 0 | 易4/中11/难5 |
| 10 | sprint | 易1 中3 难6 | 0 | 易1/中3/难6 |
| 7 | balanced | 易2 中2 难2 | 1（补中） | 易2/中3/难2 |

`sum(actual_mix) == count` 是这条算法的**不变量**，也是自动化测试的硬断言（任何蓝图、count 从 1 到 50 都必须成立）。

## 3. 知识点二：余数回补的优先级——别把难度倾向搞反

`remainder` 补给谁，决定了卷子的「口味」。蓝图本身的占比就是天然的优先级：

- 夯实（中 0.55 最高）→ 余数优先补中；
- 冲刺（难 0.60 最高）→ 余数优先补难；
- 均衡三档几乎相等 → 用稳定顺序「中 > 难 > 易」兜底，保证可复现。

关键点：**用蓝图权重排序，而不是随便补**。否则「夯实」蓝图本意是中难为主，余数若补给了「易」，就会偏离设计意图，且测试无法复现。

排序用 `(-weights[d], d)` 这个 key：先按权重降序，权重相同再按难度名保证确定性（避免 Python set 遍历顺序带来的不确定）。

## 4. 知识点三：库存回补——「某档题不够」时怎么办

`allocate` 算出的是**目标量**，但题库里某一档可能没有那么多题。比如冲刺蓝图要难 6 道，可题库里难 only 2 道。

错误做法（很多系统会这么写）：

```python
take = min(n, len(pool))
# 缺口就这么算了，total = 8 < 10，静默少题
```

用户点了 10 题，实际只拿到 8 题，**没有任何提示**。这在考试场景是硬伤——分数、掌握度、统计全基于「以为做了 10 题」。

正确做法：**缺口轮转回补到仍有余量的其它档**。

```python
deficit = count - sum(actual.values())
if deficit > 0:
    order = sorted(DIFFICULTIES, key=lambda d: (-BLUEPRINTS[blueprint][d], d))
    i = 0
    while deficit > 0 and order:
        d = order[i % len(order)]
        got = take_from(d, 1)          # 试着从这档再拿 1 道
        if got == 0:
            order = [x for x in order if x != d]  # 没货了，移出轮转
            if not order:
                break
            continue
        deficit -= 1
        i += 1
```

回补仍按蓝图权重排序——冲刺蓝图缺口优先补「难」的次高权重档（中），而不是无脑补「易」，尽量保持难度倾向。

**如果三档都凑不齐**（基础池总题量 < count），那就老老实实抛错，把判断权交还用户：

```python
if sum(actual.values()) < count:
    raise ValueError(
        f"该筛选下可组题目仅 {sum(actual.values())} 道，不足 {count} 道，"
        f"请减少数量或放宽筛选条件"
    )
```

这条错误和「纯随机组卷库存不足」的文案一致，路由统一转成 400。原则是：**能补就补，补不齐就明说，绝不静默凑数**。

## 5. 验收红线：用单测钉死三个不变量

这套逻辑用纯函数 + DB 两层测，关键是把「不变量」写成断言，而不是只测 happy path：

- **整数和不变**：`for bp: for count in 1..50: sum(allocate(count, bp)) == count`；
- **已知蓝图可复现**：`allocate(10,"intro") == {easy:6,medium:3,hard:1}` 等；
- **库存回补不静默少题**：hard 只有 2 道却要冲刺 10 道 → 实际 10 道，且 `hard==2`、`sum==10`；
- **基础池不足抛错**：每档 1 道、要 10 道 → `pytest.raises(ValueError)`；
- **题型过滤空池抛错**：只有 choice 题、要 judge → 抛错，而不是返回空卷。

把「会不会少题」这类最容易回归的隐患，用断言固化下来，比任何文档都管用。

## 6. 小结

「按比例分配整数名额」看着简单，落地要守住三条：

1. **整数化 + 余数回补**，保证 `sum == count`，不要丢题；
2. **回补优先级跟着蓝图权重走**，别把难度倾向搞反；
3. **补不齐就报错**，宁可让用户知道，也别静默凑数。

这套思路不只用于组卷——凡是「按权重把总数拆成整数桶」（限流配额、采样、A/B 分流、分页）都通用。把核心算法写成**纯函数**（`allocate` 不碰数据库），单测成本直接降一个数量级。

# 内置内容与开箱即用：把「框架」做成「产品」

> 版本：v1.7 ｜ 主题：内容工程与后台任务 ｜ 关键词：开箱即用、幂等载入、SQLite 写锁、内容质量校验、异步灌数据

## 1. 背景：新用户第一次打开系统是空的

前六个版本把能力链条搭得很完整：录资料 → 出题 → 组卷 → 考试 → 评分 → 错题本 → 掌握度 → 检索评测。
但有一个尴尬的事实：**这些内容全部依赖用户自己先录一篇资料**。

```
新用户注册 → 知识库：空 → 题库：空 → 点「生成考卷」→ 报错「库存不足」
```

也就是说，之前交付的是一个**框架**，而不是一个**可用的产品**。
用户必须自己先造数据，才能体会到它有什么用。

「开箱即用」听起来像是个文档工作，实际上是一个内容工程问题：
**把内容本身也当成交付物**，随代码一起版本化、一起评审、一起测试。

## 2. 知识点一：内容也要有数据模型——技术域 → 考点 → 题目

最容易想到但最容易做错的做法，是把题目当成一个扁平列表：200 道题干 + 答案，完事。
问题是这样组织出来的内容**和系统的其它能力没有关系**：

- 掌握度按「资料」维度聚合时，这些题不属于任何资料 → 维度缺失
- 检索评测需要「query → 期望知识块」的对应关系 → 无从建立
- 错题本想定位「哪篇资料的知识点没掌握」 → 做不了

所以内置内容按**知识图谱**组织：技术域（domain）→ 考点（topic）→ 知识库条目 → 题目。
题目通过条目标题关联到语料（`Question.entry_id`），于是前面所有能力自动成立。

| 技术域 | 题量 | 覆盖 |
|---|---|---|
| 后端-Java | 31 | 并发与线程池、锁与 AQS、集合、Spring、JVM |
| 数据库（MySQL + Redis） | 37 | 索引与锁、主从延迟、分库分表、缓存三大问题、热 key、集群容灾 |
| 分布式与架构 | 31 | 限流熔断降级、MQ 幂等与顺序、分布式事务、多活容灾、微服务治理 |
| AI 应用 | 27 | 提示与上下文工程、Agent、评测与回归、RAG / 向量检索 |
| 后端-Python | 18 | GIL、asyncio、性能分析、装饰器与上下文管理器 |
| 计算机基础 | 25 | TCP/HTTP/TLS、操作系统与 IO 多路复用、高频算法 |
| 前端 | 20 | 浏览器渲染与缓存、React 机制、性能优化 |
| 工程运维 | 18 | 容器化与 K8s、可观测性、容量与故障处置 |

**权重取舍**是这次最花心思的地方。用户给的要求很具体：前端挑高频少出，
后端除了高频和 AI 方向，还要注重高并发、容灾等生产级经验。落到数据上是两条硬约束：

- 后端域中高难度题目占比 ≥ 70%（八股题不算数）
- 整体难题占比 10%~40%（太高打击信心，太低没有区分度）

## 3. 知识点二：生产级题目怎么写

「高并发」「容灾」这类词最容易写成名词解释：问「什么是缓存穿透」，答「查询不存在的数据」。
这是知识，不是经验。经验题的标志是**有场景、有现象、有取舍、有反例**。

举三个实际写出来的例子：

**例 1（有现象）**：线程池核心 8、最大 16，压测后接口大面积超时，
监控显示线程数长期停在 8、堆内存持续上涨 → 答案是无界队列导致任务堆积，
而不是「核心线程数设置过小」。

**例 2（有取舍）**：主从延迟飙到几十秒 → 正确解是拆小事务分批提交；
而「改成半同步复制」是典型错误选项——半同步解决的是数据丢失，不是延迟。

**例 3（有反例）**：发布后半小时错误率缓慢爬升 → 资源泄漏（连接/句柄/内存），
而不是流量暴涨。这类「随时间缓慢恶化」的形态本身就是诊断线索。

写解析时坚持一条：**解析要解释为什么其它选项是错的**。
只说「答案是 B」的解析对复习没有价值；说清「A 治标不治本、C 引入了脏读、
D 是随手选的」才是把一道题变成一次经验传递。

## 4. 知识点三：载入必须幂等，否则内容无法迭代

内置内容不是一次性的：这次 207 道，下次可能补 20 道、改 5 道题的解析。
如果载入逻辑不幂等，用户重跑一次就会得到两份重复内容。

去重键的选择要贴合语义：

| 对象 | 去重键 | 理由 |
|---|---|---|
| 知识库条目 | 标题 | 同一篇资料不该有两份 |
| 题目 | 题干 + 条目 ID | 同一考点下不该有重复题干 |

副作用是正向的：**用户删掉的题会被补齐**。
这带来一个设计选择——内置题在载入时直接 `review_status = approved`，
不走审核流。审核流是给 AI 生成题准备的质量闸门，
内置题如果也要人工过一遍，就不是「开箱即用」了。

来源标记同样重要：`source = builtin / llm / rule` 三路分开统计。
顺手修了一个口径 bug——此前 `rule_count = total - llm_count`，
内置题会被算进「规则生成」，用户会以为自己录的资料生成了几百道题。
现在的断言是：三路相加必须等于总量（这条写进了冒烟测试）。

## 5. 知识点四：后台灌数据的写锁陷阱（真实踩坑）

新用户注册后要灌入 19 篇语料 + 207 道题，同步做会让注册接口卡几十秒。
所以放到后台线程——这是很自然的选择，但**自然的选择里藏着坑**。

第一版实现把 207 道题攒在**一个事务**里提交，结果冒烟测试稳定失败：

```
注册 → 立即录入资料 → sqlite3.OperationalError: database is locked → 500
```

现象是「刚注册的用户几乎不可用」。原因有两层：

1. 后台线程持有写事务几十秒，该用户其它写请求全部被挡；
2. **SQLite 的 `busy_timeout` 对这种情况不生效**——
   延迟事务（deferred）从读升级为写时遇到冲突，会立即返回 `SQLITE_BUSY`，
   不会按 busy_timeout 等待。所以只调大 `busy_timeout` 没用，必须从事务粒度解决。

修法是两条一起上：

```python
# 1) 后台载入分批提交，批次之间让出写锁
_COMMIT_BATCH = 20
_LOAD_PACE_SEC = 0.05
...
    created += 1
    pending += 1
    if pending >= _COMMIT_BATCH:
        commit_with_retry(db)
        pending = 0
        time.sleep(_LOAD_PACE_SEC)

# 2) 用户侧写操作遇到写锁时退避重试，而不是直接 500
commit_with_retry(db)   # 内部：捕获 OperationalError → rollback → 退避重试
```

修复后新用户从注册到 207 道题全部就位约 24 秒，期间正常使用不受影响。

**教训**：任何「后台批量写」的任务，都要先回答一个问题——
**它持有多长时间的写锁**？这个问题的答案决定了会不会把用户的在线操作拖垮。

## 6. 知识点五：内容质量必须自动化测试

手写内容最容易出的错是**引用错误**：题目里写了一个条目标题，但语料里没有这一篇，
这道题就会变成「无条目」的孤儿题，掌握度和检索都会少一块。
这种错误靠肉眼审 200 道题一定会漏。

所以把内容质量也写进单测，当代码一样测：

```python
def test_entry_reference_resolvable():
    titles = {e["title"] for e in knowledge_data.BUILTIN_ENTRIES}
    for spec in _all_questions():
        assert spec["entry"] in titles, f"题目引用了不存在的条目：{spec['entry']}"
```

这一条断言立刻抓出 11 道题引用了不存在的条目（JVM 内存模型、Python 装饰器）。
处理方式不是改题目去迁就，而是**补语料**——题目考到了，说明这个考点确实该有语料。
语料从 15 篇补到 19 篇。

其余几条内容断言同样有价值：

- 题干不重复（否则向量去重会把新题判为重题）
- 选择题恰好 4 个选项且答案在 A/B/C/D 内、选项前缀规范
- 填空题必须含 `______` 空位（否则前端渲染不出输入框）
- 每道题都有解析和关键词（否则错题本与检索没有素材）

## 7. 测试策略：数据规模变了，断言要跟着变

内置 207 道题进入题库后，两条原有用例挂了：

- 「随机组卷 100 道单选 → 库存不足报错」：现在真有 100 道单选了
- 「定向组卷 50 道 → 库存不足报错」：同理

这不是回归，是**数据规模变了导致前置条件失效**。
直接删掉用例是错的（丢掉了「库存不足要友好报错」这条保障），
正确做法是让前置条件继续成立：把组卷范围限定到**本次冒烟新建的资料**
（题目数远小于 100），断言依然稳定。

同理，E2E 里「知识库列表能看到某条种子资料」的断言，
在列表按 id 倒序、首页只显示 10 条的情况下会失效，
改为断言首页确实可见的内置语料，并且**不再写死具体资料标题**，
只校验「至少 8 行 + 首页可见的语料名」，避免以后扩充语料又挂。

**教训**：断言依赖的数据规模要显式化。写死「库存不足」时，
要先确认「为什么不足」，把这个原因固定下来，而不是固定数字。

## 9. 经验清单

1. **内容是交付物**：要和组织代码一样版本化、评审、测试，不能只当资源文件丢进仓库。
2. **内容要有结构**：题目关联到知识点条目，才能让检索、掌握度、错题本自动复用。
3. **经验题 > 名词题**：有场景、有现象、有取舍、有反例，解析要解释为什么其它选项是错的。
4. **载入必须幂等**：去重键贴合语义（标题 / 题干+条目），顺带获得「删掉能补齐」的能力。
5. **来源要分开统计**：`builtin / llm / rule` 三路相加等于总量，这条要写成断言。
6. **后台批量写要分批提交**：先回答「持有多久写锁」，SQLite 的 busy_timeout 救不了延迟事务升级冲突。
7. **内容质量要自动化测试**：引用可解析、题干不重复、选项规范、解析不为空。
8. **数据规模变了，断言的前置条件要重写**：固定「原因」而不是固定「数字」。

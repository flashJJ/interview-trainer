# v1.7 内置知识库与题库（开箱即用）

> 版本：v1.7 | 日期：2026-10-25 | 状态：已交付
> 前置：v1.6 掌握度与定向训练

## 1. 目标与动机

v1.6 之前，系统的「内容」全部依赖用户自己录入：先录一篇资料，再点 AI 出题。
这在演示与真实首用场景里有个致命问题——**新用户第一次打开系统是空的**：

| 环节 | 没有 LLM Key | 有 LLM Key |
|---|---|---|
| 知识库 | 空 | 空 |
| 题库 | 空 | 空（要先录资料、再等出题） |
| 首次组卷 | 直接报错「库存不足」 | 要等一轮出题完成 |

也就是说，v1.6 之前的系统是一个**框架**，而不是一个**可用的产品**。
v1.7 要解决的就是「开箱即用」：把内容也随产品一起交付。

**需求边界（用户明确给定）：**

1. 题库来源：**手写精选**，不做 LLM 批量生成——质量可控、可离线、可评审。
2. 覆盖范围：**传统全栈为主 + AI 方向补强**。
3. 规模：**约 200 道**，其中「前端挑高频少出一些；Java / Python 等后端除了高频与 AI 方向，
   还要注重高并发、容灾等生产级经验考核」。

## 2. 内容组织：技术域 → 考点 → 题目

内置内容按知识图谱的方式组织，而不是散装列表：

```
技术域（domain）          考点（topic）              题目
────────────────────────────────────────────────────────
后端-Java      并发编程 / 集合与框架 / JVM        31 道
后端-Python    并发与性能 / 语言特性              18 道
数据库         MySQL 高并发 / Redis 缓存架构      37 道
分布式架构     高并发防护 / 一致性与容灾 / 治理    31 道
AI 应用        提示工程 / Agent / 评测 / 向量检索 27 道
前端           浏览器与 React                     20 道
基础           网络 / 操作系统 / 算法             25 道
工程运维       容器化 / 可观测性 / 故障处置        18 道
                                        合计 207 道
```

**题目通过条目标题关联到知识库语料**（`Question.entry_id`），这样三点收益自动成立：

- 掌握度可以按「资料」维度聚合（v1.6 的能力直接可用）
- 出题 / 检索能拿到对应知识块（v1.5 的混合检索直接可用）
- 错题本与定向练习能定位到「哪篇资料的知识点没掌握」

### 2.1 覆盖范围与权重取舍

| 维度 | 数量 | 说明 |
|---|---|---|
| 题型 | 选择 137 / 判断 38 / 填空 32 | 选择为主，填空判断作为补充 |
| 难度 | 简单 27 / 中等 134 / 困难 46 | 中等为主，困难占 22% 保证区分度 |
| 后端域中高难度占比 | ≥ 70% | 落实「重生产级经验」的要求 |

生产级题目的写法与八股不同，优先考「线上会遇到什么坑、怎么排查、怎么取舍」，例如：

- 线程池核心线程 8、最大 16，压测后线程数长期停在 8 且堆内存上涨 → 无界队列
- 主从延迟几十秒 → 大事务拆批，而不是换半同步
- 缓存全挂 → 限流熔断降级丢卒保车，而不是调大连接池
- 发布后半小时错误率缓慢爬升 → 资源泄漏，而不是流量暴涨

## 3. 载入链路设计

### 3.1 幂等

| 对象 | 去重键 | 重复执行的行为 |
|---|---|---|
| 知识库条目 | 标题 | 已存在则跳过 |
| 题目 | 题干 + 条目 ID | 已存在则跳过，被删掉的会补齐 |

这意味着内容迭代时（例如新增 20 道题）只需重跑一次，不会重复写入，
也不会覆盖用户自己改过的题目。

### 3.2 自动过审

内置题 `review_status = "approved"` 直接进组卷池。
开箱即用的内容不该让用户先过一遍审核流——审核流是给 AI 生成题准备的。

### 3.3 来源标记

| 字段 | 值 | 用途 |
|---|---|---|
| `Question.source` | `builtin` / `llm` / `rule` | 题库列表筛选与徽标 |
| `KnowledgeEntry.source_type` | `builtin` / `text` / `file` / `url` | 知识库列表徽标 |

统计口径同步修正：此前 `rule_count = total - llm_count` 会把内置题算进「规则生成」，
现在三路分开统计，保证「内置 / 规则 / AI」三者相加等于总量。

### 3.4 触发时机

| 场景 | 行为 |
|---|---|
| `python seed.py` | 建 demo 用户后自动载入内置内容 |
| `python seed.py --builtin` | 给已有用户补内置内容（幂等） |
| 新用户注册 | 注册接口返回后**后台线程**载入，不阻塞注册响应 |

## 4. 关键实现决策与踩坑

### 4.1 后台载入必须分批提交（真实 Bug）

最初实现把 207 道题攒在一次事务里提交，结果**注册后的用户几乎不可用**：
后台线程长时间独占 SQLite 写锁，该用户其它写请求直接 `database is locked` → 500。
冒烟测试在「注册 → 立即录入资料」这一步稳定复现。

> 关键点：SQLite 的 `busy_timeout` 对「延迟事务从读升级为写」的冲突**不会**等待，
> 会立即返回 `SQLITE_BUSY`。因此不能只依赖 `busy_timeout`，必须从事务粒度上解决。

修法（两处一起改）：

1. `load_builtin_questions` 每 20 条提交一次，批次间 `sleep(0.05)` 让出写锁；
2. 用户侧写操作（如知识库录入）改用 `commit_with_retry`，遇到写锁退避重试。

修复后新用户从注册到 207 道题全部就位约 24 秒（本地向量化），期间正常使用不受影响。

### 4.2 语料与题库必须交叉校验

题库文件里引用条目标题是字符串，写错会导致题目变成「无条目」的孤儿题，
掌握度资料维度与检索都会少一块。因此在单测里加了交叉校验：
**每道题引用的条目标题必须能在内置语料中找到**。
首批 11 道题引用了尚不存在的条目，据此补了两篇语料（JVM、Python 装饰器），
语料总数从 15 篇增加到 19 篇。

### 4.3 冒烟测试的库存不足用例需要跟着数据变

内置 207 道题进入题库后，「随机组卷 100 道单选」不再库存不足（此前只有 15 道）。
这不是回归，而是数据规模变了。两个用例改为**限定到本次冒烟新建的资料**，
让「库存不足」这个断言继续稳定成立，而不是简单删掉用例。

## 5. 验证结果

| 层次 | 结果 |
|---|---|
| 单元测试 | 154 passed（新增 `tests/test_builtin.py` 14 项） |
| 冒烟测试 | 120 通过 / 0 失败（新增 §7.8 内置内容 5 项） |

| 种子数据 | 27 条知识库（19 内置）/ 279 道题（207 内置） |

单测覆盖三类：`语料与题库本身的质量`（重名、字段合法、条目可解析、题型难度分布、
生产级占比）、`载入链路`（自动过审、来源标记、关联条目）、`幂等`（重复载入不重复写、
删掉后能补齐）。

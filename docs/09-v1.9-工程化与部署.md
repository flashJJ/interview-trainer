## 1. 现状盘点（实测，2026-10-27）

| 项 | 实测值 | 对方案的含义 |
|---|---|---|
| 后端代码 | `backend/app` 1 MB | 构建上下文小，镜像体积由依赖决定 |
| 运行时数据 | `backend/data` 20 MB（DB 3 MB + WAL 4 MB + Chroma） | 必须外置为卷，不能烤进镜像 |
| 前端产物 | `frontend/dist` 3 MB | nginx 静态托管足够 |
| 本地 venv | 456 MB | 直接 COPY venv 不可行，镜像内重装依赖 |
| Python | 3.13.14 | 与 `python:3.13-slim` 对齐 |
| 重依赖 | `chromadb 1.5.9` + `chromadb_rust_bindings` + **`onnxruntime 1.31.1`** | 镜像会偏胖（预估 1.2–1.6 GB），是体积主要来源 |
| 前端 | 有 `package-lock.json`（114 KB） | 可用 `npm ci` 保证可重复构建 |
| 验证现状 | pytest 169 / smoke 124 / E2E 18 步 | 全部手工跑，CI 化收益最大 |
| Docker | 29.2.0 / Compose v5.0.2，daemon 正常 | 本地可完整验收 |

### 现状差距（必须补的洞）

1. 无 `Dockerfile` / `docker-compose.yml` / `.dockerignore`。
2. `scripts/smoke_test.py` 的 `BASE` **硬编码** `http://127.0.0.1:8000/api`，无法指向容器端口。
3. `requirements.txt` 把 `pytest` 混进运行依赖（生产镜像多装测试框架）。
4. `jwt_secret` 有硬编码默认值，`.env.example` 里还有另一个占位串 `please-change-me-in-production` —— **两个变体都得拦**，否则直接部署等于所有人共享签名密钥（安全红线）。
5. CORS 只允许 `localhost:5173/4173`，容器化后端口不同会被拦（需同源反代规避）。
6. 无 CI，全靠本地手工验证。

## 2. 方案设计

### 2.1 拓扑

```
浏览器 ──▶ frontend (nginx:80) ──┬── 静态资源 dist（SPA fallback）
                                 └── /api/*  ──▶ backend:8000 (uvicorn)
                                                        │
                                                  named volume: app-data
                                                  ├── interview_trainer.db
                                                  └── chroma/
```

- 宿主端口 **8080 → 容器 80**（80 在开发机上常被占）。
- 前后端**同源**（都走 8080），CORS 不再参与；后端 CORS 白名单保持不变即可。
- 后端**不对外暴露**端口，只走 compose 内网 + nginx 反代（减少攻击面）。

### 2.2 后端镜像（`backend/Dockerfile`）

- 两阶段：`builder` 装编译依赖并 `pip install --prefix=/install`，`runtime` 只拷 `/install`，避免把 gcc 带进最终镜像。
- 基础镜像 `python:3.13-slim`；`PYTHONUNBUFFERED=1`、`PIP_NO_CACHE_DIR=1`。
- **非 root**：`appuser`(uid 10001)，`/app` 与 `/app/data` 归属该用户。
- 层缓存顺序：先 `COPY requirements.txt` + `pip install`，再 `COPY app/`。
- 健康检查用标准库，避免装 curl：
  `HEALTHCHECK CMD python -c "import urllib.request;urllib.request.urlopen('http://127.0.0.1:8000/api/health')"`
- 体积目标：首版 ≤ 1.5 GB，优化目标 1.2 GB（见风险 R2）。

### 2.3 前端镜像（`frontend/Dockerfile`）

- `builder`：`node:22-alpine` + `npm ci` + `npm run build`（脚本已含 `tsc --noEmit`，构建即类型检查）。
- `runtime`：`nginx:1.27-alpine`，只拷 `dist` 与 `nginx.conf`。
- `nginx.conf` 三件套：
  - `try_files $uri $uri/ /index.html`（React Router 深链不 404）
  - `location /api/ { proxy_pass http://backend:8000; }`（同源反代）
  - `client_max_body_size 20m`（PDF/DOCX 导入，后端 `python-multipart` 上限对齐）
- 体积目标：≤ 60 MB。

### 2.4 编排（`docker-compose.yml`）

| 项 | 取值 | 说明 |
|---|---|---|
| `backend.environment` | `DATABASE_URL=sqlite:////app/data/interview_trainer.db` | **四个斜杠**（绝对路径），少一个就写进容器层，重启即丢 |
| | `CHROMA_DIR=/app/data/chroma` | 与 DB 同卷，备份即全量 |
| | `JWT_SECRET=${JWT_SECRET:?}` | 未设置直接起不来，强制显式配置 |
| `backend.volumes` | `app-data:/app/data` | **named volume**，不用 Windows bind mount（SQLite WAL 在 bind mount 上易出锁异常） |
| `backend.healthcheck` | `/api/health`，`interval 10s / timeout 3s / retries 6 / start_period 30s` | 供 frontend `depends_on: condition: service_healthy` |
| `frontend.ports` | `8080:80` | 唯一对外入口 |
| `restart` | `unless-stopped` | 开机自恢复 |
| `env_file` | `.env`（可选，缺省用默认值） | LLM/Embedding Key 走这里，不进镜像 |

### 2.5 配置与安全

- 已有 `backend/.env.example`（LLM/Embedding 说明很完整），本版**扩写**而非新建：补 `DATABASE_URL` / `CHROMA_DIR` / 端口说明，并把 `JWT_SECRET` 占位串改为显式「必须替换」。
- **启动即校验**：`JWT_SECRET` 命中默认串（`change-me-in-production-...`）或样例串（`please-change-me-in-production`）时，`lifespan` 里 fail-fast（生产）或打印醒目警告（开发）。判定口径统一收到一个常量集合里，含单测。
- 上传大小三处对齐：nginx `client_max_body_size`、FastAPI 默认、前端提示文案。

### 2.6 首次启动体验

空卷启动 → `init_db()` 建表 → 用户注册时后台线程分批载入内置内容（19 篇资料 / 207 题 / 20 条评测用例，20 条一批提交）。

- 文档需写明「注册后等待约 30–60 秒，内容逐步出现」；
- 备选一键灌注：`docker compose exec backend python seed.py --builtin`（幂等），同时创建 `demo/demo123`。

### 2.7 CI（`.github/workflows/ci.yml`）

| Job | 内容 | 时间预算 |
|---|---|---|
| `backend-test` | `setup-python@v5`(3.13, pip cache) → `pip install -r requirements.txt` → `pytest -q` | ≤ 3 min |
| `backend-smoke` | 后台起 uvicorn → 轮询 `/api/health`（最长 60 s）→ `SMOKE_BASE=... python scripts/smoke_test.py` | ≤ 5 min |
| `frontend-build` | `setup-node@v4`(22, npm cache) → `npm ci` → `npm run build` | ≤ 3 min |
| `docker-build`（P1） | `docker buildx bake` 两个镜像，不推送 | ≤ 6 min |

- 触发：`push`（`main` / `develop` / `feature/**` / `v1.9-planning`）、`pull_request`。
- `concurrency` 同分支取消旧任务；`permissions: contents: read`；三 job 并行，总时长以最慢者为准。
- 冒烟前置改造：`smoke_test.py` 的 `BASE = os.environ.get("SMOKE_BASE", "http://127.0.0.1:8000/api")`。

> **红线 R1**：推 `.github/workflows/**` 需要 token 具备 `workflow` scope。当前 `gh auth token` 的 scopes 是 `gist, read:org, repo`，**缺 workflow**，直推会被 GitHub 拒绝。落地前需 `gh auth refresh -s workflow`（浏览器授权）或改用具备 `workflow` 的 classic PAT。

### 2.8 E2E 是否入 CI

暂不。原因：E2E 脚本驱动系统 Edge（`channel: msedge`），GitHub runner 无 Edge；改 chromium 需 `npx playwright install --with-deps`，+5–8 min，收益低于成本。列为 P2，v1.9 仍本地跑。

## 3. 验收标准（可量化）

| # | 项 | 标准 |
|---|---|---|
| 1 | 冷启动 | `docker compose up -d --build`（首次构建除外）后 **≤ 90 s** `/api/health` 返回 200 |
| 2 | 主链路 | 注册 → 内置内容自动载入（19 资料 / 207 题 / 20 用例）→ 蓝图组卷「夯实 ×10」（易 2 / 中 6 / 难 2） |
| 3 | 持久化 | `docker compose restart` 后用户与试卷仍在；`down`（不带 `-v`）不丢数据 |
| 4 | 安全 | 容器内 `id -u` ≠ 0；未设 `JWT_SECRET` 时容器明确报错退出 |
| 5 | 体积 | backend ≤ 1.5 GB、frontend ≤ 60 MB |
| 6 | CI | 三个 job 全绿，**总时长 ≤ 8 min** |
| 7 | 回归 | pytest 169 / smoke 124 保持全绿，E2E 18/18 本地仍绿 |

## 4. 风险与对策

| # | 风险 | 概率/影响 | 对策 |
|---|---|---|---|
| R1 | 缺 `workflow` scope 导致 CI 文件推不上去 | 高 / 阻塞 | 实施前 `gh auth refresh -s workflow`；保留 classic PAT 作备选 |
| R2 | `onnxruntime` 使后端镜像膨胀到 1.5 GB+ | 中高 / 中 | 多阶段 + 分层缓存；实测后评估 chromadb 是否可去掉 onnx 额外依赖（本项目用自研确定性向量，不走 chromadb 默认 embedding） |
| R3 | Windows bind mount 上 SQLite WAL 锁异常 | 中 / 高 | 一律 named volume；文档禁止改回 bind mount |
| R4 | 非 root 用户对 `/app/data` 无写权限 | 中 / 高 | 镜像内 `chown -R 10001:10001 /app/data`；compose 不用 `user:` 覆盖 |
| R5 | 前端上传大文件 413 | 中 / 中 | nginx `client_max_body_size 20m` 与后端上限对齐 |
| R6 | 冒烟打不到容器端口 | 确定 / 低 | `SMOKE_BASE` 环境变量 + compose 内直连 `http://backend:8000/api` |
| R7 | 首次注册内置载入被误判「卡住」 | 中 / 低 | 文档写明 30–60 s；前端已有进度提示则复用 |
| R8 | 默认 JWT 密钥上公网 | 低 / 灾难 | 启动 fail-fast（§2.5），CI 里也断言该行为 |
| R9 | 镜像构建拉包慢 | 中 / 低 | Dockerfile 支持 `PIP_INDEX_URL` 构建参数（默认官方源） |

## 8. 关键假设

1. 目标环境有 Docker 24+ 与 Compose v2+（本机 29.2/v5.0.2，已满足）。
2. 生产仍用 SQLite + ChromaDB（单机单实例场景），并发写不高；PG 迁移不在本版。
3. GitHub Actions 对 public 仓库不限分钟数，CI 成本可忽略。
4. 用户具备 `gh auth refresh -s workflow` 的操作条件（否则 CI 只能先本地保留文件、后续再推）。

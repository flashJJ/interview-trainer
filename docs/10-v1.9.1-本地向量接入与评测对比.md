# v1.9.1 接入本地向量模型与评测对比

> 版本：v1.9.1 | 日期：2026-10-27 | 状态：已交付
> 前置：v1.9 容器化与 CI；同日已接通火山方舟 LLM（Agent Plan 套餐）

## 1. 背景：LLM 有了，向量还是「字面哈希」

v1.5 上线混合检索时，向量通道用的是**内置确定性向量**——中文 n-gram TF-IDF 哈希到 384 维。
它的定位是「零配置可跑」，不是「好用」：同义词、改写句、跨语言术语全都抓不住。

接入真实 LLM 后，出题质量上来了，但**出题取材与去重仍走这套哈希向量**，成为整条链路的质量瓶颈。

### 为什么不用云端 Embedding

实测了现有方舟套餐 Key 的两种用法，都不通：

| 尝试 | 结果 |
|---|---|
| 套餐 Key → 标准端点 `/api/v3/embeddings` | **401** `AuthenticationError`（套餐 Key 与标准端点隔离） |
| 套餐 Key → 套餐端点 `/api/plan/v3/embeddings` | **404** `UnsupportedModel`（套餐不提供 embedding 模型） |

结论：embedding 要么单独买标准方舟的接入点，要么用第三方（SiliconFlow / 百炼），要么**用本机模型**。
选本机：零成本、免网络、数据不出本机，代价是占显存。

## 2. 方案：Ollama + qwen3-embedding:0.6b

Ollama 暴露 OpenAI 兼容的 `/v1/embeddings`，所以**后端代码一行没改**，只改配置：

| 配置项 | 值 |
|---|---|
| `EMBEDDING_BASE_URL` | `http://localhost:11434/v1`（容器内用 `http://host.docker.internal:11434/v1`） |
| `EMBEDDING_API_KEY` | 任意非空串（Ollama 不校验，但代码要求非空才启用） |
| `EMBEDDING_MODEL` | `qwen3-embedding:0.6b` |

实测：单条 embedding **251 ms**，维度 **1024**；模型常驻显存约 **2.4 GB**。

## 3. 迁移：四个步骤 + 三个坑

新增 `backend/scripts/reindex_embeddings.py`：

```bash
cd backend
python scripts/reindex_embeddings.py --dry-run   # 目标维度 vs 存储维度
python scripts/reindex_embeddings.py --reset     # 维度变化时：删集合 → 全量重算
# 重启后端服务
```

### 坑 1：ChromaDB 维度由首次写入决定

现有集合是 384 维，直接写入 1024 维会报
`Dimensionality of (1024) does not match collection dimensionality (384)`。
必须先删集合重建（脚本的 `--reset`），且**脚本会拒绝在不一致时静默写入**。

### 坑 2（最坑）：重新分块会让评测用例的期望块 ID 全部失效

第一版脚本图省事，直接调 `process_entry()` 重建条目——它会删掉旧 chunk 行、插入新行、**主键全变**。
而检索评测用例的 `expected_ids` 记的是旧主键。后果：

```
vector recall 0.2333 → 0.0000
bm25   recall 0.4583 → 0.0000   ← 连不依赖向量的 BM25 也归零
```

「BM25 也归零」正是关键线索：说明不是向量质量问题，而是**评测基准本身指向了不存在的块**。

修正：迁移只重算向量，**不重新分块**——直接遍历现有 `KnowledgeChunk` 逐条 `upsert`，主键不动。
已损坏的用例删除后按当前块重新解析（内置 20 条用例可从 `data/builtin/eval_cases.py` 一键重载）。

### 坑 3：集合被删除后，进程内句柄失效

重建是在另一个进程里做的，正在运行的服务仍持有旧 collection 句柄，接口直接 500。
**迁移后必须重启服务**（脚本结尾会打印提醒）。

### 坑 4：语义评分阈值是按哈希向量标定的

换模型后填空题的语义分档直接失真。实测同一组答案对：

| 答案对 | qwen3-embedding 相似度 | 应有结果 |
|---|---|---|
| 布隆过滤器 ↔ 布隆过滤机制 | 0.956 | 满分 |
| 布隆过滤器 ↔ 使用布隆过滤器来解决 | 0.889 | 满分（包含关系兜底） |
| 布隆过滤器 ↔ 缓存空值 | 0.539 | **0 分**（原阈值给半分） |
| TCP 三次握手 ↔ UDP 无连接 | 0.678 | **0 分**（原阈值给半分） |

真实模型会把「同领域但答错」推到 0.5–0.7。修法：阈值按 Embedding 实现分档。

```python
SEMANTIC_THRESHOLDS = {"api": (0.80, 0.92), "local": (0.50, 0.80)}  # (半分, 满分)
```

## 4. 量化结果（同一份 20 条内置评测集、149 个知识块）

| 模式 | 指标 | 384 维哈希 | **1024 维 qwen3** | 变化 |
|---|---|---|---|---|
| vector | Recall@5 | 0.2333 | **0.6250** | **+39.2 pp** |
| vector | MRR | 0.3583 | **0.7958** | +43.8 pp |
| vector | Hit@1 | 0.2500 | **0.7000** | +45.0 pp |
| bm25（对照组） | Recall@5 | 0.4583 | 0.4583 | 0（预期不变） |
| hybrid | Recall@5 | 0.4417 | **0.6000** | +15.8 pp |
| hybrid | MRR | 0.6600 | **0.8000** | +14.0 pp |

**对照组的意义**：BM25 一分不动，证明指标变化全部来自向量通道，评测本身没有漂移。

## 5. 结论与后续

1. 向量通道 Recall@5 从 0.23 提到 0.63，**纯语义检索已经超过 BM25**（0.63 vs 0.46）；
2. 但 **hybrid（0.60）反而略低于纯 vector（0.625）** —— 等权 RRF 在「向量强、BM25 弱」时会拖后腿，
   下一版应做 RRF 权重标定（或按查询类型路由），这是现成的优化点；
3. 迁移成本集中在「评测基准的稳定性」，而非向量计算本身——**评测集是资产，动数据结构前先想它**；
4. 阈值、权重这类超参必须与 Embedding 实现绑定，不能全局共享。

## 7. 补充：RRF 权重扫描（同一评测集）

既然纯 vector（0.625）反超 hybrid（0.600），就扫了一遍 `vector_weight`（BM25 权重恒为 1.0）：

| vector_weight | Recall@5 | MRR | Hit@1 |
|---|---|---|---|
| 0.3 | 0.5333 | **0.8167** | **0.7000** |
| 0.5 | 0.5833 | **0.8167** | **0.7000** |
| 1.0（当前默认） | 0.6000 | 0.8000 | 0.6500 |
| 1.5 | 0.6000 | 0.7917 | 0.6500 |
| 2.0 | **0.6750** | 0.7683 | 0.6000 |

结论：**这是一条无法靠调参同时优化的曲线**——权重越高 Recall 越好、MRR/Hit@1 越差。
高权重把更多语义相关块塞进 top-5（召回升），但打乱了最相关那条的排名（MRR 降）。

**但更要紧的是：这组数字不足以支撑改默认值。**
20 条用例里改变 1 条就动 5 个百分点，2.0 相比 1.0 的 +7.5pp 只相当于 1.5 条题，处在噪声量级。
在样本放大之前调权重，本质是对这 20 条题过拟合。

所以本版**保持默认 1.0 不变**，把结论留档。正确的下一步是：

1. 用 `/retrieval/cases/auto` 把评测集扩到 100+ 条（不同主题、不同问法）；
2. 再做一次扫描，用置信区间而不是单点值判断；
3. 真要上线，按场景分权重：**出题取材**（top-8，重召回）用 2.0，**搜索框**（重首条）用 0.5。

# 前端重构规划（v1.5 重构版）

> 版本：计划稿 | 日期：2026-10-24 | 状态：**待决策**
> 前置：v1.4 功能完成（10 个业务页面 + 讲题抽屉），E2E 13 步全绿

---

## 1. 先澄清一个事实

**当前前端已经是完整的 React 工程**，不是"简单的前端页面"：

```text
React 18.3 + TypeScript 5.6 + Vite 5.4 + Ant Design 5.29
ECharts 5（图表） + axios + react-router 6
源码 5,193 行：11 个页面 + 2 个共享组件
构建产物：tsc 严格模式 0 错误 + vite build 通过
```

所以"重构成 React"不是目标——**目标是重构 React 工程内部的组织方式**。你感受到的"不便于改动、难定位问题"，是可量化的工程债务造成的：

## 2. 问题诊断（带数据）

| # | 问题 | 数据/证据 | 影响 |
|---|---|---|---|
| 1 | **单文件巨型页面** | `KnowledgeBase.tsx` **706 行**（统计卡+语义搜索+表格+详情抽屉+新建弹窗+出题弹窗 6 块逻辑全在一个文件） | 改一处要在 700 行里翻，容易碰坏其他逻辑 |
| 2 | **API 层未按域拆分** | `client.ts` **616 行**（11 个业务域全挤一个文件），`types.ts` 368 行 | 找接口要全文搜索，类型定义与实现分离难 |
| 3 | **共享组件几乎为零** | 11 个页面只有 **2 个**共享组件（AppLayout、AITutorDrawer） | 统计卡/表格/空状态/分页在各页重复实现 5~8 次 |
| 4 | **数据获取模板代码重复** | 每个页面手写 `useState + useEffect + try/catch + loading + 分页 + 刷新`，8 个页面重复同一套 | 改一处错误处理要改 8 个文件；列表状态（分页/筛选）无统一管理 |
| 5 | **内联样式散落** | 全项目 200+ 处 `style={{...}}`，无样式体系 | 视觉调整靠逐个改 JSX，一致性差 |
| 6 | **路由未懒加载** | 首屏单 chunk **2.3MB**（gzip 749KB） | 首屏慢；改动一个页面导致整包失效 |
| 7 | **无错误边界** | 任何页面运行时异常 → 整棵树白屏 | 线上"白屏"难定位，只能靠控制台 |
| 8 | **HMR 抖动放大"难定位"体感** | 长跑 dev server 反复热更后样式注入抖动（今天已两次遇到） | 视觉问题分不清是代码 bug 还是环境问题 |

## 3. 方案对比

### 方案 A：渐进式工程内重构（推荐）

保留 React 18 + AntD + Vite 技术栈，分四阶段治理工程债务。**每阶段独立可交付、可回滚，功能不停摆。**

- 引入 **TanStack Query** 统一服务端状态（消灭 8 个页面的手写加载/错误/刷新样板）
- **API 层按域拆分**（`api/knowledge.ts`、`api/exam.ts`…）+ 统一响应类型
- **页面拆组件**（706 行的 KnowledgeBase → 6 个组件；共享组件从 2 个 → 10+ 个）
- **feature-based 目录**（`features/knowledge/{api,hooks,components,page}`）
- **路由懒加载 + ErrorBoundary + 路径别名 + ESLint/Prettier**

### 方案 B：Next.js App Router 全量重写

- 劣势：SSR 对本项目无收益（纯内网单机工具）；重写成本 ≥ 15 人天；功能冻结期长；AntD 与 RSC 兼容摩擦
- 结论：❌ 投入产出比差

### 方案 C：最小治理（只拆巨页）

- 仅拆分 `KnowledgeBase.tsx` + 抽 5 个公共组件，2 人天
- 劣势：模板代码、API 层、目录结构问题原样保留，半年后同样痛点复发
- 结论：可作为"时间紧张时的保底选项"

| 维度 | A 渐进式 | B Next.js 重写 | C 最小治理 |
|---|---|---|---|
| 解决痛点的彻底程度 | ★★★★★ | ★★★★★ | ★★ |
| 成本（人天） | 8-10 | 15+ | 2 |
| 功能冻结风险 | 低（分阶段） | 高 | 无 |
| 可回滚性 | 高 | 低 | 高 |
| 对已有测试的破坏 | 低（E2E 守行为） | 高（需重写） | 低 |

## 4. 推荐方案 A：分四阶段执行

### 阶段 1：工程地基（约 1.5 人天）

| 事项 | 说明 |
|---|---|
| 路径别名 | `@/` → `src/`，消灭 `../../..` 相对路径 |
| ESLint + Prettier | 风格统一，提交前自动检查（`lint` script） |
| **ErrorBoundary** | 页面级错误边界 + 错误上报到 console/UI 提示（不再整树白屏） |
| **路由懒加载** | `React.lazy + Suspense` 拆分页面 chunk，首屏 ≤ 800KB |
| **API 层按域拆分** | `api/http.ts`（axios 实例/拦截器）+ `api/knowledge.ts` / `api/questions.ts` / `api/exams.ts` / `api/analytics.ts` / `api/chat.ts` / `api/settings.ts` / `api/wrong-questions.ts` |
| TanStack Query 接入 | `QueryClientProvider` + 统一 queryKey 约定 + 全局错误处理 |

**验收**：构建产物 chunk 数 ≥ 8、首屏 ≤ 800KB、ErrorBoundary 注入后人为抛错不白屏、`npm run lint` 通过。

### 阶段 2：数据层迁移（约 2.5 人天）

- 为每个域写 Query hooks：`useEntries()`、`useQuestions(filters)`、`useWrongQuestions()`、`usePracticeAnalytics()`…
- 8 个页面替换手写 `useState+useEffect` 为 hooks（loading/error/refetch/缓存失效自动）
- 写操作统一 `useMutation` + 成功后 `invalidateQueries`（出题后题库/统计自动刷新，不再手动 `load()`）

**验收**：页面内 `useEffect` 数量减少 ≥ 60%；删除手动 `load()` 调用；E2E 13/13 全绿。

### 阶段 3：组件抽取（约 3 人天）

| 文件 | 目标 |
|---|---|
| `KnowledgeBase.tsx` 706 行 | → `page`（<120 行）+ `StatsCards` + `SemanticSearch` + `EntryTable` + `EntryDetailDrawer` + `CreateEntryModal` + `GenerateQuestionsModal` |
| `Review.tsx` 358 行 | → `page` + `ReviewTable` + `EditQuestionModal` |
| `QuestionBank.tsx` 334 行 | → `page` + `QuestionFilters` + `QuestionTable` + `QuestionDetailModal` |
| `WrongQuestions.tsx` 332 行 | → `page` + `WrongStats` + `WrongTable` |
| 共享组件库 | `StatCard`（统一统计卡颜色语义）、`PageHeader`、`EmptyState`、`StatusTag`、`DifficultyTag`、`QTypeTag`、`ConfirmDelete` |

**验收**：单文件 ≤ 300 行；共享组件 ≥ 10 个；E2E 13/13 全绿。

### 阶段 4：目录重组与样式收敛（约 2 人天）

- 目录从 `pages/` 平铺改为 `features/<域>/`（api/hooks/components/page），`shared/` 放通用组件与工具
- 内联 `style={{}}` 收敛：高频布局样式 → CSS Modules；颜色/间距 → antd token 统一
- 路由表集中到 `app/routes.tsx`

**验收**：目录按域组织；内联 style 数量减少 ≥ 50%；E2E 13/13 全绿；构建 0 错误。

## 9. UI / 布局专项（用户反馈驱动的 6 个连环缺陷）

这一串问题都不是"调个颜色"就能了事的，每个都有独立的 CSS 机制成因，记录在此便于回归排查。

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 深色侧栏上"题目审核"文字看不清（黑字压黑底） | antd `Badge` 的 CSS 强制 `color: rgba(0,0,0,0.88)`，且 `style` prop 不透传（`inlineStyle: null`） | 弃用 Badge，手写红点徽标并显式 `color: inherit` |
| 2 | 表格内容溢出卡片、无滚动条 | 页面 Table 未配 `scroll`，容器 `overflow: visible` | 各表加 `scroll={{ x }}` + 操作列 `fixed: 'right'` |
| 3 | 操作按钮"拒绝"被截断 | 按钮组 248px > 列宽 210px | 文案"编辑后通过"→"编辑"，列宽 220px（按钮 206px） |
| 4 | 页面四周一圈白边，内容不贴合视口 | 项目没有任何全局重置，浏览器默认 `body { margin: 8px }` | `index.html` 内重置 `html, body, #root { margin:0; padding:0; height:100% }` |
| 5 | 整页一起滚动，侧栏会滚出视野 | 布局用 `min-height` 撑高，滚动发生在 document 层 | 外层 `height:100vh; overflow:hidden`，Content `flex:1; minHeight:0; overflow:auto` |
| 6 | 表格滚很长后看不见列名 | Table 未开 `sticky` | 5 个列表页加 `sticky={stickyTableConfig}`（见 `utils/stickyTable.ts`） |

**第 6 项踩到的两个隐藏坑（改布局时勿踩）**：

1. **`overflow: hidden` 会劫持 sticky 的滚动参照物。** 白色卡片上原有一句 `overflow: hidden`（早期用来挡横向溢出）。它让该 div 成为 sticky 元素的"最近滚动容器"，但它自身永远不滚动 → 表头跟着内容一起滚走，`position: sticky` 形同虚设。祖先链上任何一层 `overflow: hidden / auto / scroll` 都要检查。
2. **滚动容器的 `padding` 会被算进 sticky 约束矩形。** Content 原有 `padding: 24`，Chrome 以滚动容器的 **padding box** 作为 sticky view rectangle，表头吸附位置就比内容区顶部低了 24px，滚动的行会从那条缝里露出来。改为内边距由白色卡片自己承担。

> 验证基线：`pytest 81 / smoke 72 / E2E 13` 全绿；两档视口（1440×900、1093×620）逐页探针确认 `pageScrollable=false`、`pageOverflowX=false`、表头吸附 `top === 内容区 top`、侧栏与顶栏恒为 0。

# v1.10 扫描件（图片型 PDF）OCR 支持

> 版本：v1.10 | 日期：2026-10-28 | 状态：已交付
> 前置：v1.9 容器化、v1.9.1 本地向量接入（Ollama qwen3-embedding）

## 1. 背景：pypdf 只能读「文本层」

导入链路一直是 `pypdf` 读文本层。遇到扫描件（整页是图、没有字符对象）时，提取结果为空，
系统直接报「内容太少」。这不是 bug，是能力边界——之前明确写着「不做 OCR」。

真正的问题是：**用户手里大量资料就是扫描件**（拍照的讲义、盖章的文档、老 PDF）。
所以这一版把它补上，但只补「图变字」这一层。

## 2. 选型：为什么是 pypdfium2 + RapidOCR

| 方案 | 渲染 PDF | OCR 引擎 | 结论 |
|---|---|---|---|
| PyMuPDF (`fitz`) | ✅ 快、质量好 | 不含 | ❌ **AGPL**，开源仓库传染性太强 |
| pdf2image + Tesseract | ✅ 但要装 poppler | 需装二进制 + `chi_sim` 语言包 | ❌ 依赖外部系统包，容器体积和部署复杂度都上去 |
| **pypdfium2 + rapidocr-onnxruntime** | ✅ BSD，纯 wheel | ✅ Apache，ONNX，复用镜像里已有的 onnxruntime | ✅ 采纳 |

关键收益：**不引入第二套推理引擎**（onnxruntime 本就在，chromadb 依赖它），
也不需要任何外部二进制，`pip install` 就完事。

## 3. 判定与流程

```
上传 PDF
  └─ pypdf 提取文本层
       ├─ 每页平均字符 ≥ 50  → 走原路径（零额外成本）
       └─ < 50（扫描件/只剩页码）
              ├─ OCR 依赖不可用 → 明确报错（不静默降级）
              └─ pypdfium2 逐页渲染（scale=2.0 ≈ 144 DPI）→ RapidOCR → 行重排
```

判定阈值 `looks_like_scan(text, pages) = len(text)/pages < 50`：
正常文字页 800–2000 字/页，扫描件通常只剩页眉页码，< 30 字/页，区分度足够。

## 4. 三个实现细节（不做就会很难看）

1. **行重排**：RapidOCR 返回的是文本框，直接按返回顺序拼会串行。按 `min(y)` 分组
   （纵向容差 14px），组内按 `x` 排序拼接；中文直接相连、英文之间补空格。
2. **低置信度丢弃**：`score < 0.35` 的行直接丢，主要是噪点和页边装饰。
3. **页眉页脚去重**：只去掉**连续重复**的整行，避免误杀正文里的合法重复。

## 5. 踩到的坑：opencv 需要 X11

`rapidocr-onnxruntime` 依赖 `opencv-python`（GUI 版），它在 `python:3.13-slim` 里导入直接失败：

```
ImportError: libxcb.so.1: cannot open shared object file
```

本地 Windows 跑得好好的（自带 DLL），容器里必炸——**又是「本地能跑」类问题**。

两种修法：

| 方案 | 代价 |
|---|---|
| 装 `libxcb1 libgl1 libglib2.0-0` | +40–60 MB，且保留了用不到的 GUI 依赖 |
| **换 `opencv-python-headless`** | 服务端只用图像解码，GUI 版毫无意义；实测体积反而小 ~50 MB |

采用后者：在 builder 阶段 `pip uninstall -y opencv-python && pip install opencv-python-headless`。
一行换来的效果：镜像从 1.25 GB 回到 **1.2 GB**，且不再依赖任何 X11 库。

## 6. 实测数据

| 指标 | 数值 | 条件 |
|---|---|---|
| 单页识别耗时 | **约 4–5 s** | 1240×1754（A4@150DPI），CPU |
| 首次调用额外开销 | 5–10 s | ONNX 模型加载（进程内只发生一次） |
| 识别置信度 | **0.90–0.94** | 合成样本，宋体 30px |
| 端到端上传（1 页扫描件） | **3.3 s**（容器，模型已热）/ 14.5 s（首次） | 含 OCR + 分块 + 向量化 |
| 镜像体积 | 886 MB → **1.2 GB**（+314 MB） | 主要来自 opencv + onnx 模型 |

## 7. 限制（写清楚，不粉饰）

1. **默认只 OCR 前 10 页**（`OCR_MAX_PAGES` 可调）。单页 4–5 s，20 页就要 100 s，
   同步请求会把体验拖死；下一步应改成后台任务 + 进度条。
2. **表格结构仍然丢**。OCR 只把像素变成字，列对齐在渲染那一刻就没了。
   表格密集的资料依然建议先转 Markdown / 「列名：值」的句子。
3. **错字会被出题放大**。把「1000」认成「1OOO」这种，导入后生成题目时会继承错误，
   所以扫描件导入后建议人眼过一遍再出题。
4. **只处理中文/英文**。RapidOCR 默认模型以中英为主，其它语种识别率未验证。
5. **前端上传超时改为 300 s**（原全局 60 s），因为 OCR 是分钟级操作。

## 8. 验收

```bash
# 单测（7 项：判定逻辑 + 合成扫描件端到端 + 页数截断）
python -m pytest tests/test_ocr.py -q

# 真实链路：上传一份只有图像的 PDF，应返回 status=ready 且 chunk_count≥1
# （前端：知识库 → 导入 → 选择扫描件 PDF）
```

结果：`pytest 197 passed`；开发实例上传 **3.3–14.5 s** 完成，容器内同样通过（headless cv2 5.0.0）。

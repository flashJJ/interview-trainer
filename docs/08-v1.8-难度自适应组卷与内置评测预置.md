## 1. 功能一：难度自适应组卷

### 1.1 现状

`POST /exams/generate`（`backend/app/routers/exams.py:83`）当前支持：
- `difficulty: Optional[str]` —— 指定**单一**难度（easy/medium/hard），不填则全难度随机混合；
- `types` / `count` / `entry_ids` 筛选。

痛点：想练"以中等为主、穿插少量困难"的模拟卷，只能手动反复调 `difficulty` 跑多次，没有一次成型的能力。

### 1.2 方案

在 `GenerateExamIn` 增加 `blueprint: Optional[str]`（难度蓝图）。服务端优先级：

```
若 payload.difficulty 有值        → 单一难度（现有行为，蓝图忽略）
否则若 payload.blueprint 有值      → 自适应分配（本版本新增）
否则                              → 纯随机（现有默认行为）
```

**蓝图定义**（写进 `backend/app/services/exam_service.py` 常量，便于单测）：

| blueprint | 名称 | easy | medium | hard | 定位 |
|---|---|---|---|---|---|
| `intro` | 入门 | 60% | 30% | 10% | 刚学完一轮，建立信心 |
| `consolidate` | 夯实（推荐默认） | 20% | 55% | 25% | 面试主练，中等偏上 |
| `balanced` | 均衡 | 33% | 34% | 33% | 摸底真实水平 |
| `sprint` | 冲刺 | 10% | 30% | 60% | 临门一脚，专攻难题 |

**分配算法**（`adaptive_questions`，纯函数、可单测）：
1. 基础池：`approved + active + q_type∈types + (entry_ids 可选)`，与现有 `generate_exam` 完全一致；
2. 按蓝图比例把 `count` 拆成三档目标量（整数，按比例向下取整，余数加到最大档，保证合计 = `count`）；
3. 逐档从可用题随机抽样；**若某档可用量 < 目标量**，取光该档，把缺口按比例回补到其他仍有余量的档（最多两轮，保证不静默少题）；
4. 三档合并后 `random.shuffle`；
5. 若基础池总量 < `count` → 抛 `400`，文案与现有「库存不足」一致（"该筛选下可组题目仅 N 道…"）。

**考卷元数据**：`ExamPaper.config` 增加 `mode` 字段（`random|single|adaptive`）、`blueprint`、`actual_mix`（如 `{easy:4,medium:11,hard:5}`），用于标题与「我的考卷」展示。
标题自动生成：`自适应考卷 · 夯实 ×20（中 11 / 难 5 / 易 4）`（非自适应时保持现有标题规则）。

### 1.3 前端改动（`frontend/src/pages/Practice.tsx`）

- 在「难度（可选）」下方新增「难度蓝图」`Select`：选项 = 不限(纯随机) / 入门 / 夯实 / 均衡 / 冲刺；
- 选中非空蓝图时，禁用「难度（可选）」`Select`（二者互斥，避免歧义）；
- `GenForm` 增加 `blueprint?: string`；`onGenerate` 透传 `blueprint`；
- `frontend/src/api/types.ts` 的 `GenerateExamIn` 增加 `blueprint?`；`frontend/src/api/exams.ts` 透传。

### 1.4 验收标准（难度自适应）

- 单元：蓝图分配在各档库存充足时精确命中比例；某档不足时正确回补且总量 = `count`；总量不足时抛 400；
- 单测覆盖 easy/medium/hard 三档边界与整数取整余数分配；
- E2E：走通"选蓝图→生成→进入考试→提交评分"，考卷 `config.mode==adaptive`、标题含蓝图名；
- 现有「随机」「指定难度」「定向」组卷 E2E 不受影响（回归）。

## 2. 功能二：内置内容检索评测预置

### 2.1 现状

- 检索评测用例来源只有 `auto`（从用户知识块反推，存在同源泄漏、需 LLM 才质量好）与 `manual`（手工录入）。
- 新用户 `docs/07` 已自动载入 19 篇内置语料（已分块 + 向量化）+ 207 道内置题，但**检索评测页仍是空的**——v1.5 最核心的"量化对比"卖点开箱不可用。
- `docs/05` / `retrieval_eval.py` 明确：**手写用例 > 自动用例**，但项目没随箱带手写用例。

写作原则（与内置语料一致）：查询用**改述 / 从原理提问**，不复刻条目原文连续词组，规避 `retrieval_eval.py` 指出的同源泄漏；每条映射到 19 篇内置条目之一。

**载入器**（在 `backend/app/services/builtin.py` 新增 `load_builtin_eval_cases`）：
- 建 `title -> entry_id -> chunk_ids`（从 `KnowledgeChunk` 取该用户内置条目的全部块 id）；
- 逐条：按 `entry` 标题解析到 `chunk_ids`，写 `RetrievalEvalCase(user_id, query, expected_ids_json=json.dumps(chunk_ids), source="builtin", origin_chunk_id=0, note="内置预置")`；
- 幂等：按 `(user_id, query)` 去重；条目标题找不到的跳过并记日志（19 篇均存在，正常不触发）；
- 挂到 `load_builtin`（在 `load_builtin_questions` 之后调用，此时块已就绪）；新用户后台线程 `load_builtin_async` 自动覆盖。

**手动触发端点**（方便已清空用例 / 老用户补齐）：`POST /retrieval/eval-cases/builtin` —— 对当前用户幂等载入内置评测用例，返回 `(created, skipped, total)`。

**seed.py**：`--builtin` 路径额外调用 `load_builtin_eval_cases`；`--reset` 清空评测用例（用户数据整体清空，符合现有语义）。

### 2.3 前端改动（`frontend/src/pages/RetrievalReport.tsx`）

- 「来源」列新增 `builtin` → 标签「内置」（金色/蓝色，区别于「手工/自动」）；
- 在「评测集」操作区新增「载入内置用例」按钮，调用 `POST /retrieval/eval-cases/builtin`（幂等，已存在则 skipped）；
- `frontend/src/api/types.ts` 的 `EvalCase['source']` 联合类型增加 `'builtin'`；`frontend/src/api/retrieval.ts` 增加 `loadBuiltinCases()`。

### 2.4 验收标准（内置评测）

- 单元 `test_builtin_eval.py`：
  - 用例数 ≥ 18，每条 `entry` 能在 19 篇内置条目中找到；
  - 防泄漏：query 不包含其映射条目正文里连续的 ≥12 字子串（用滑动窗口校验，允许少量术语重合）；
  - `expected_ids` 非空且全部属于该条目；
- 集成：新用户载入后 `RetrievalEvalCase` 中 `source="builtin"` 数量 = 用例数；重复载入不翻倍；
- 冒烟 §7.9：评测用例数 ≥ 18、存在 `source=builtin`、运行一次评测返回 hybrid Recall@K；
- E2E：「内置评测用例开箱即用」——内置标签可见、点「运行评测」出报告。

## 6. 风险与缓解

| 风险 | 缓解 |
|---|---|
| 蓝图某档库存不足导致体验差 | 回补算法保证不静默少题；总量不足走现有 400 文案 |
| 内置评测用例查不到条目 | 载入时按标题解析，找不到跳过并日志；19 篇均存在，单测兜底 |
| 同源泄漏使指标虚高 | 手写查询刻意改述；评测页已声明"横向比相对差异"；单测加防泄漏校验 |
| 与现有随机/指定难度组卷冲突 | 优先级清晰（difficulty > blueprint > random），E2E 回归覆盖 |

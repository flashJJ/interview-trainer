# v1.5 检索增强与评测

> 版本：v1.5 | 分支：`feature/v1.5-rag-eval` | 日期：2026-10-25
> 前置：v1.4（AI 流式讲题）已完成

## 1. 版本目标

把「检索」从一个黑盒函数，变成**可度量、可调参、可复现**的工程模块。

三件事：

| 目标 | 交付 |
|---|---|
| 检索质量提升 | 向量 + BM25 混合召回，RRF 名次融合，查询改写 |
| 有据可依 | 14 条评测集（查询 → 期望块），Recall@5 / MRR@10 / Hit@1 三指标 |
| 可调可控 | 融合权重可调、改写可开关；报告页可下钻到逐用例逐模式的名次 |

## 2. 为什么原来的检索不够用

改造前只有一条路径：`knowledge.search_chunks(embedding)` — 纯向量检索。

三个已存在的问题：

1. **内置向量本质是词法匹配。** 零配置模式下 `embed_text()` 是中文 2/3-gram 的哈希向量，它没有任何语义泛化能力（"高可用"与"故障转移"在向量空间里毫无关系）。它比 BM25 少了 IDF 与长度归一化，所以严格来说**比 BM25 更弱**。
2. **出题与讲题根本没有走检索。** 出题是把某条资料的全部块直接喂给模型，讲题只取 `chunk_id` 同资料的前 2 块——即"检索"从未参与生成链路，RAG 只是名义上的。
3. **没有任何评估手段。** 改了参数好不好，只能靠"感觉"。

v1.5 只解决第 1、3 条（第 2 条属于 v1.6 的定向训练范围）。**先有度量，再谈优化**——这是本版本最重要的取舍。

## 3. 技术方案

### 3.1 BM25：自己写，不引依赖

`app/services/bm25.py`，约 100 行纯 Python：

```
idf(t)   = ln(1 + (N - df(t) + 0.5) / (df(t) + 0.5))        # Lucene 变体，恒为正
score(q,d) = Σ_t idf(t) · tf(t,d)·(k1+1) / (tf(t,d) + k1·(1 - b + b·|d|/avgdl))
k1 = 1.5, b = 0.75
```

三个决定：

| 决定 | 理由 |
|---|---|
| 不引入 jieba 分词 | 项目已有的 `tokenize()` 就是中文 2/3-gram；字符 n-gram 做 BM25 在中文技术文本上可用，且零依赖、零词典维护 |
| 不引入 rank_bm25 库 | 语料百~千块量级，纯 Python 线性打分是微秒级；少一个依赖就少一个部署风险 |
| 建倒排 `_postings` | 只对命中的 term 打分，避免每次查询扫全语料的所有 term |

### 3.2 融合：RRF，不是分数加权

两种分数量纲完全不同：余弦 ∈ [0,1]，BM25 无上界（实测 2~10）。归一化后再加权，权重对数据分布极敏感，换一批语料就得重调。

RRF 只看名次：

```
RRF(d) = Σ_i w_i / (k + rank_i(d))      k = 60（原论文取值）
```

`w_i` 就是报告页暴露的「向量权重」，默认 1.0，BM25 恒为 1.0。

### 3.3 查询改写

- **规则版**（永远可用）：抽关键词串，去掉"是什么/怎么/为什么"的疑问壳 → 多一条检索式；
- **LLM 版**（配置了 Key 才启用）：让模型输出 2 条术语密集的检索式；
- 改写产出的多条检索式各自召回，再一起进 RRF——本质是 multi-query retrieval。

任何改写失败都静默降级到原始查询，不影响检索可用性。

### 3.4 索引缓存

BM25 索引一次构建多次复用。缓存键是 `(块数量, 最大块 id)`——知识块在本系统里"随资料处理一次性生成、随资料删除一起消失"，这两个值一变就说明语料变了。

线程安全：FastAPI 的同步路由跑在线程池里，缓存字典加 `threading.Lock`。

## 4. 评测设计

### 4.1 用例怎么来

| 来源 | 做法 | 适用 |
|---|---|---|
| 自动 | 按资料轮转抽样知识块（长度 ≥ 40 字，避免信息量不足），反推一条查询 | 快速建立评测集 |
| 自动 + LLM | 同上，但让模型**换一种说法**提问 | 推荐：贴近真实提问 |
| 手工 | 人写真实问题 + 选定期望块 | 严格口径 |

**这里有一个关键教训。** 最初自动生成用的是"块内 top-3 关键词 + 是什么"，结果三种模式全部 Recall@5 = 1.000——查询本身就把答案写在里面了，评测完全失去区分度。必须让查询**改述**而不是抄词，才有评测价值。这是评测集设计里最容易踩的坑。

### 4.2 指标定义

| 指标 | 定义 | 看什么 |
|---|---|---|
| Recall@K | 命中期望块数 / 期望块总数，再对全部用例取平均 | 召回是否漏 |
| MRR@10 | 首个命中名次倒数的平均 | 正确结果排得够不够靠前 |
| Hit@1 | 首位即命中的比例 | 用户第一眼看到的对不对 |

### 4.3 已知局限（写进页面和文档，不藏）

自动用例由知识块自身反推，存在同源词面泄漏，**指标绝对值偏乐观**。因此报告页的结论口径是「同一批次内的横向对比」，需要绝对数字时用手工用例。

## 5. 实测结果

环境：内置词法向量（未配置 Embedding API）、19 个知识块、14 条 LLM 改述用例、`top_k=5`。

**run#1：向量权重 = 1.0（RRF 等权）**

| 模式 | Recall@5 | MRR@10 | Hit@1 |
|---|---|---|---|
| 纯向量 | 78.6% | 0.482 | 28.6% |
| 纯 BM25 | **100%** | **0.929** | **85.7%** |
| 混合 | **100%** | 0.762 | 57.1% |
| 混合 + 改写 | **100%** | 0.881 | 78.6% |

**run#2：向量权重 = 0.5**

| 模式 | Recall@5 | MRR@10 | Hit@1 |
|---|---|---|---|
| 混合 | **100%** | 0.917 | 85.7% |
| 混合 + 改写 | **100%** | 0.917 | 85.7% |

### 结论（四条，都能被上面的数字支持）

1. **混合检索找回了向量漏掉的 21.4 个百分点。** 纯向量 Recall@5 = 78.6%，混合 = 100%。漏掉的用例集中在"精确术语"型查询（如"RAG 问答系统有哪些关键环节"），哈希向量把语义拉平了，BM25 靠术语精确命中救回来。
2. **但等权融合会把排名质量拉低。** 混合 MRR 0.762 < 纯 BM25 0.929：弱通道的名次噪声把原本第一的正确块往后推。**通道越多不等于越好。**
3. **降权立刻修复。** 向量权重 1.0 → 0.5，MRR 0.762 → 0.917、Hit@1 57.1% → 85.7%，而 Recall 仍是 100%。这就是"有评测集"的直接价值——参数不是拍的，是量出来的。
4. **查询改写对弱通道有纠偏作用。** 等权时改写把 Hit@1 从 57.1% 拉到 78.6%（+21.5pt）；权重降到 0.5 后，改写与不改写持平（此时 BM25 已足够强，改写带来的边际收益消失）。**改写的收益取决于另一条通道有多弱**，这个结论只有把两档都跑一遍才能得到。

> 一句话总结：当前配置下真正的功臣是 BM25，向量通道是"补召回但拖排名"的角色。要让它变成正向贡献，需要接真实语义 embedding —— 那时应当用同一套评测集重跑，再决定权重复位到多少。这正是把评测集固化下来的意义。

## 6. 接口契约

```
POST /api/knowledge/search        # 检索（mode=vector|bm25|hybrid，默认 hybrid）
  → results[].channels / vector_score / bm25_score   # 命中来自哪些通道、各通道打分

GET  /api/retrieval/overview      # 用例数 / 知识块数 / 最近一次运行
GET  /api/retrieval/chunks        # 知识块候选（手工录入用例时选期望块）
GET  /api/retrieval/cases         # 评测集
POST /api/retrieval/cases         # 手工新增（query + expected_ids）
POST /api/retrieval/cases/auto    # 自动生成（count, use_llm）
DEL  /api/retrieval/cases[/{id}]  # 删除单条 / 清空
POST /api/retrieval/run           # 运行评测（top_k, use_rewrite, vector_weight）
GET  /api/retrieval/runs[/{id}]   # 历史 / 明细
```

## 7. 工程细节

- **LLM 生成评测集必须并发**：单条实测 16~40s，串行 14 条要 8 分钟；服务端 `ThreadPoolExecutor(6)` 降到约 2.5 分钟，写入仍在主线程串行（避免 SQLite 并发写）。
- **评测时复用 embedding**：同一查询要在多个模式下重复使用，`embedding_cache` 把 Embedding API 调用次数从 `用例数 × 模式数 × 查询式数` 降到 `用例数 × 查询式数`。
- **删除过短块**：`MIN_CHUNK_CHARS = 40`，太短的块反推查询没有区分度。
- **查询撞车自动扩词**：同主题多块容易生成同名查询，逐级加词直到唯一，仍重复则跳过并计数。

## 9. 遗留与下一版

- 检索尚未接入**出题链路**（出题仍取单条资料的全部块）。v1.6 的「按薄弱知识点定向出题」会用到它。
- 自动评测集存在同源泄漏，手工用例目前只能在界面上逐条录，缺少批量导入。
- 融合权重目前是"每次运行传入"，还没有固化为系统配置项（因为当前最优值依赖 embedding 后端，固化反而误导）。
